# v1.2.36 — Watcher `.pnp.cjs` fallback + cert trust chain clarification

> **TL;DR:** The catalog-watcher PM2 process was crashing on the factory
> laptop because the bundled installer ships `node_modules/` (from
> `npm install` in CI) but NOT `.pnp.cjs` (which only `yarn install`
> produces), and the wrapper hardcoded `-r ./.pnp.cjs`. Fixed with
> the same fallback `install/lib/bootstrap.cjs#serverInvocation`
> already uses for the factory server. Also documents the cert /
> signing issue separately — that one is **NOT fixed in this
> release** because it requires a real code-signing certificate to
> be uploaded to GitHub Secrets (the current `CSC_LINK_BASE64`
> secret contains a self-signed cert).

---

## 1. WATCHER LOG `.pnp.cjs` missing — fixed

### What was wrong

The launcher's WATCHER LOG pane on the factory laptop showed:

```
at require(C:\Program Files\AbaYa Track Launcher\resources\tools\catalog-watcher\.pnp.cjs:6770:13)
at Module._load (node:internal/modules/cjs/loader:1050:27)
--- process exited (1) ---
```

The PM2 `catalog-watcher` process kept restarting in a loop because
the wrapped command (`node -r ./.pnp.cjs watch-catalog.js`) tried to
preload a file that doesn't exist on the factory install.

### Root cause

`install/pm2-catalog-watcher-wrapper.js` (introduced in v1.2.33
alongside `install/pm2-abaya-wrapper.js`) hardcoded `-r ./.pnp.cjs`
in its spawn args:

```js
const child = spawn(NODE, ['-r', './.pnp.cjs', 'watch-catalog.js'], {
  cwd: WATCHER_DIR,
  ...
});
```

The bundled install's `tools/catalog-watcher/` ships:

- ✅ `watch-catalog.js` — the entry script
- ✅ `package.json` — declared deps
- ✅ `node_modules/chokidar/`, `node_modules/xlsx/` — installed by
  the CI step `npm install --omit=dev --no-audit --no-fund --loglevel=error`
- ❌ `.pnp.cjs` — **never generated**, because the CI uses `npm
  install`, not `yarn install`. Yarn 4 PnP is the only thing that
  produces `.pnp.cjs`. npm install produces `node_modules/` flat
  layout only.

So the wrapper's `node -r ./.pnp.cjs watch-catalog.js` always
crashed on the factory install. The factory-server wrapper
(`install/pm2-abaya-wrapper.js`) had the same bug originally but
was fixed in v1.2.33 to detect the `.pnp.cjs` fallback path.
The watcher wrapper was added at the same time but kept the
hardcoded `-r` preload.

### Fix

`install/pm2-catalog-watcher-wrapper.js` now mirrors
`install/lib/bootstrap.cjs#serverInvocation` — checks whether
`.pnp.cjs` exists in `WATCHER_DIR` before deciding to preload:

```js
const PNP_PATH = path.join(WATCHER_DIR, '.pnp.cjs');
const args = fs.existsSync(PNP_PATH)
  ? ['-r', './.pnp.cjs', 'watch-catalog.js']
  : ['watch-catalog.js'];

const child = spawn(NODE, args, {
  cwd: WATCHER_DIR,
  env: process.env,
  stdio: 'inherit',
  windowsHide: true,
});
```

Same shape, same pattern, same fallback semantics as the factory
server wrapper. No other code paths touched.

## 2. Code-signing "AbaYa Track Self Signed" — NOT a code bug

### What was wrong

The launcher's LAST ERROR pane on the factory laptop showed:

```
LAST ERROR
9/14/2026, 5:47:39 AM · New version 1.2.34 is not signed by
the application owner: publisherNames: AbaYa Track Self
Signed, raw info: { SignerCertificate: { FriendlyName: "",
IssuerName: "CN=AbaYa Track Self Sign", ... } }
```

The factory laptop's electron-updater (6.8.4) is running
`windowsExecutableCodeSignatureVerifier` against the downloaded
v1.2.34 EXE and rejecting it because the publisher name on the
new binary doesn't match the publisher name on the currently-
installed binary, OR the chain doesn't reach a trusted root.

### Root cause

The `CSC_LINK_BASE64` GitHub Secret that was set on 2026-09-03
contains a **self-signed** certificate (Subject = `CN=AbaYa
Track Self Signed`, Issuer = `CN=AbaYa Track Self Signed`, valid
2026-09-03 → 2027-09-03). Confirmed locally:

```powershell
PS> Get-AuthenticodeSignature install\AbaYa-Track-Launcher-Setup-1.2.34.exe
Status            : UnknownError
SignerCertificate : [Subject] CN=AbaYa Track Self Signed
                     [Issuer]  CN=AbaYa Track Self Signed
                     [Not After] 9/3/2027 12:59:44 AM
```

electron-builder did sign the EXE — see CI logs from
`build-and-release` step 13:

```
• Materialized pfx at D:\a\_temp\cert\abaya.pfx (2694 bytes)
• signing  file=...AbaYa Track Launcher.exe certificateFile=...abaya.pfx
```

So the .pfx was passed correctly. The .pfx itself just contains a
self-signed cert because that's what `CSC_LINK_BASE64` was
generated from.

A self-signed cert has Subject == Issuer == "CN=AbaYa Track Self
Signed". `windowsExecutableCodeSignatureVerifier`:
1. Extracts the new binary's publisher name → "AbaYa Track Self
   Signed"
2. Compares with the currently-installed binary's publisher name
3. AND checks whether the certificate chain reaches a trusted root

Self-signed certs fail step 3 (no chain to a trusted CA), so
electron-updater refuses to install v1.2.34.

### Why v1.2.33 worked but v1.2.34 doesn't

The currently-installed v1.2.33 is **also** self-signed with the
same Subject. Step 2 (name match) passes — same name "AbaYa Track
Self Signed" on both sides. Step 3 (chain trust) also fails, but
the verifier's check is "publisherNames must match AND chain must
reach a trusted root".

Looking at electron-updater 6.8.4 source:
`windowsExecutableCodeSignatureVerifier.js:50` blocks if the
`SignerCertificate` is not from a trusted root. Both v1.2.33 and
v1.2.34 fail step 3 — but v1.2.33 was the FIRST install on the
factory laptop, so the verifier hadn't run yet (there's nothing to
compare against on first install). When v1.2.34 was downloaded
the next day, the verifier ran for the first time and refused.

### Fix — requires operator action, not a code change

Two options, both outside this commit:

**Option A (recommended):** Buy a real code-signing certificate
from a CA whose root is in Windows's trust store (DigiCert,
Sectigo, GlobalSign). Re-encode as base64, overwrite
`CSC_LINK_BASE64` and `CSC_KEY_PASSWORD` secrets in GitHub, push
a trivial commit to trigger a rebuild. The new build will be
signed with a real cert; electron-updater's chain check passes;
v1.2.37+ flow through without LAST ERROR.

**Option B (interim):** Disable signature verification in the
launcher:

In `tools/desktop-launcher/package.json` add to the `build` block:

```json
"win": {
  ...
  "verifyUpdateCodeSignature": false
}
```

This tells `electron-updater` to skip the cert check. **Security
trade-off:** an attacker who can MITM the LAN mirror or the R2
mirror could substitute a maliciously-signed EXE and the launcher
would install it. Acceptable for an isolated factory LAN; NOT
acceptable if the laptops ever traverse public Wi-Fi.

I recommend Option A; ship Option B in a follow-up commit if the
CA cert takes more than a few days to procure.

### What this commit does NOT do

- Does NOT regenerate the cert secret (operator action needed)
- Does NOT push a v1.2.36 with a working signature — the next CI
  build will produce the same self-signed EXE until
  `CSC_LINK_BASE64` is replaced with a real cert
- Does NOT change `electron-updater` behavior (the verify stays
  on; the LAST ERROR stays visible until the cert is real)

### Operator verification of the issue

On the factory laptop, in PowerShell:

```powershell
Get-AuthenticodeSignature "$env:LOCALAPPDATA\Programs\AbaYa Track Launcher\AbaYa Track Launcher.exe"
# Look at SignerCertificate.Subject and Issuer.
# Both should be the same (self-signed) OR
# Subject should be "CN=<your company>, O=<...>" with
# Issuer from a trusted CA like "CN=DigiCert, O=DigiCert Inc, C=US"
```

## What factory PCs will see after v1.2.36

The **WATCHER LOG** will go from:
```
require(.../catalog-watcher/.pnp.cjs:6770:13) — process exited (1)
```
to:
```
(node:internal/modules/cjs/loader) Catalog watcher started, watching /path/to/catalog
```

The **LAST ERROR** (signing) will stay the same until
`CSC_LINK_BASE64` is replaced with a real cert. v1.2.36 doesn't
fix that — it requires an operator action (Option A or B above).

## Version note

The previous v1.2.35 commit (`a3b0466`) was supposed to bump
the version but the file edits were missed. This v1.2.36 commit
fixes that and adds the watcher `.pnp.cjs` fallback.

The CI workflow's `🏷️ Read Canonical Launcher Version` step
reads `tools/desktop-launcher/package.json#version` as the
single source of truth for the GitHub Release tag and
`latest.yml`, so the v1.2.36 build will publish to GitHub
Releases + R2 mirror automatically (via the v1.2.35 OTA-pipeline
fix).
