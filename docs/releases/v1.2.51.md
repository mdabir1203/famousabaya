# v1.2.51 — LAN tombstone defends the kiosk against cloud-stale "Arman Reza resurrection"

> **TL;DR:** When a worker tapped Finish at the kiosk, the LAN
> immediately removed them from the local view — but `refreshCloudToday`
> (every 30 s) re-added them ~30-60 s later from a stale `active_sessions`
> row on the cloud (the `session_finish` push was still in flight or
> queued for retry). The kiosk flashed "Working" again until the cloud
> caught up. v1.2.51 fixes this with a 5-minute in-memory **recent-finish
> tombstone** keyed by `emp_id` — while the tombstone is live, the
> cloud-active merge skips that worker so the LAN's "this worker is
> finished" view stays authoritative until the cloud catches up.

---

## 1. The bug

### 1.1 What the operator reported

> "Fix the kiosk issues. As Arman Reza, one of the employees, when
> taps end of work logoff — after some moments the kiosk starts showing
> him in working mode again."

The supervisor and the worker (Arman Reza, EMP135, `e_bc_00000135`) saw
the same flash on every Finish tap that didn't get a clean, instant
`session_finish` push — typically the ones that hit a network blip,
auth retry, or simply took longer than the refresh interval.

### 1.2 The data

Reproducible from any factory laptop on a flaky-Wi-Fi moment. Even on
clean networks the flash was visible on most Finish taps because the
30-second `refreshCloudToday` interval is shorter than the typical
`session_finish` push latency (200 ms-2 s on healthy network, up to 30 s
on a busy cell tower).

The flash lasted anywhere from ~200 ms (when the cloud had already
processed the deletion) to ~30 s (when the push queued for retry).

### 1.3 The root cause

`server.js → req_finishWork` does three things in sequence on a worker
Finish tap:

1. `delete ACTIVE_SESSIONS[emp_id]` — local map cleared.
2. `broadcastState()` — every kiosk client receives the new state;
   Arman disappears from the live board within ~50 ms.
3. `pushToCloudflare('session_finish', cfPayload)` — pushes the finish
   event to the cloud's D1 worker.

Step 3 is best-effort. The cloud may take 200 ms-30 s to actually
delete the matching row from `active_sessions` (worker latency + retry
queue + eventual consistency on the LAN side). The push can also fail
(network blip, auth rejection, worker 5xx); it then sits in the
`ceo-ingest-queue.jsonl` retry buffer for up to 30 s before the next
attempt (`CEO_INGEST_RETRY_MS`).

Meanwhile, `setInterval(refreshCloudToday, 30 * 1000)` runs every 30 s
and pulls the cloud's view of active sessions. The merge code at
`server.js:2169-2200` did this for each cloud row:

```js
const local = ACTIVE_SESSIONS[empId];
if (local) {
  // Update display fields only — trust local for abaya_id / started_at
  ...
  stats.activeReplaced++;
} else {
  // The LAN has no entry for this emp_id, so trust the cloud's view.
  ACTIVE_SESSIONS[empId] = { ... };
  stats.activeAdded++;
}
```

The merge unconditionally re-added Arman from the cloud's stale row.
Then `broadcastState()` fired again — and the kiosk briefly showed
him as working again.

The bug had been documented in the existing `req_finishWork` comment
at `server.js:2501-2504`:

> "if we skip this push, refreshCloudToday (every 30 s) re-merges the
> row and the LAN dashboard shows the employee as active again —
> indefinitely, because the cloud never gets a session_finish to DELETE it."

But the bug also occurred when the push was **slow** (in flight) or
**queued for retry** — there was a window where the cloud had Arman
active but the LAN didn't, and the merge re-added him. The existing
comment only covered the "skip the push entirely" failure mode.

## 2. The fix

A new short-lived tombstone per `emp_id` on the LAN server. While the
tombstone is live, `refreshCloudToday`'s merge skips that `emp_id` so
the LAN's "Arman is finished" view stays authoritative until the cloud
catches up.

### 2.1 The tombstone helper (`shared/recent-finish-tombstone.cjs`)

A pure, testable Map-backed tombstone with a configurable TTL:

```js
const { makeRecentFinishTombstone } = require('./shared/recent-finish-tombstone.cjs');
const ts = makeRecentFinishTombstone({ ttlMs: 5 * 60 * 1000 });
ts.note('e_bc_00000135');           // LAN just finished Arman
ts.isLive('e_bc_00000135');         // true for the next 5 minutes
ts.isLive('e_bc_00000135', futureMs); // false once TTL elapses
ts.consume('e_bc_00000135');        // manual removal
ts.pruneExpired();                  // memory hygiene
ts.size();                          // active tombstone count
```

Default TTL is 5 minutes — comfortable against any realistic push-
retry cadence (the cloud's retry interval is 30 s, so 5 min covers
~10 retry cycles). Configurable via the `RECENT_FINISH_TOMBSTONE_MS`
environment variable (floor 30 s). Forgiving on bad input: non-string
`emp_id`s, `null`, `undefined`, empty/whitespace strings are ignored.

### 2.2 The merge helper (`shared/cloud-active-merge.cjs`)

The previous inline merge loop in `server.js → refreshCloudToday` was
extracted to a pure helper that takes `getLocal` / `setLocal` callbacks
and a tombstone. This makes the merge logic + tombstone defense
unit-testable without spinning up a full server subprocess:

```js
const { mergeCloudActiveIntoLocal } = require('./shared/cloud-active-merge.cjs');
const stats = mergeCloudActiveIntoLocal(cloudActive, {
  getLocal: (empId) => ACTIVE_SESSIONS[empId],
  setLocal: (empId, sess) => { ACTIVE_SESSIONS[empId] = sess; },
  bcToLocalEmp,
  tombstone: recentFinishTombstone,
});
// stats = { activeAdded, activeReplaced, activeSuppressedByTombstone }
```

Per-row behavior is unchanged except for the new tombstone defense:

| Situation                                | Action                       |
|------------------------------------------|------------------------------|
| `emp_id` missing / not in cloud shape    | skip (existing)              |
| Tombstone live for this `emp_id`         | skip + count as suppressed   |
| `ACTIVE_SESSIONS` already has the entry  | update display fields only   |
| Otherwise                                | create the entry             |

### 2.3 Where the tombstone gets noted

Three call sites:

- `server.js → req_finishWork` (line ~2483) — the worker-tapped-Finish
  path. The tombstone is set immediately after
  `delete ACTIVE_SESSIONS[emp_id]`.
- `server.js → /api/admin/close-stale-sessions` (line ~2642) — the
  operator-driven orphan-close path. Same defense.
- The boot-time `dropGhostActiveSessions` sweep (v1.2.32) does NOT
  tombstone — it deletes ghosts outright before any cloud merge can run.

### 2.4 Where the tombstone gets consumed

`server.js → refreshCloudToday` — the cloud-active merge loop now
checks `recentFinishTombstone.isLive(empId)` for each row. A live
tombstone increments `stats.activeSuppressedByTombstone` and skips
the row.

### 2.5 Memory hygiene

A `setInterval` runs every 60 s and calls
`recentFinishTombstone.pruneExpired()`. Without this, a long-running
factory server could accumulate tombstones across the whole shift
(worst case: 60 finishes/min × 5 min TTL = ~300 entries — modest but
untidy). The prune logs `[recent-finish-tombstone] pruned N expired
entries` only when there's something to report.

Tombstones are intentionally lost on server restart — that's correct
behavior: on restart the LAN re-hydrates `ACTIVE_SESSIONS` from the
offline-report snapshot, and a stale cloud row would correctly
re-hydrate any worker that is actually still on the floor.

### 2.6 Cross-laptop scope — known gap, documented

Tombstones are per-process / in-memory only. If Laptop A's
`session_finish` push fails AND Laptop B is running, Laptop B's
`refreshCloudToday` could still resurrect the worker. Fixing that
requires either a cloud-side tombstone or LAN coordination, neither of
which is in scope for v1.2.51. The 5-minute TTL still bounds the
problem (after 5 min the cloud's stale row will eventually trigger a
visible resurrection, surfacing the underlying push failure to the
operator rather than hiding it forever).

## 4. Operator action items

**Immediate:** Refresh the dashboard. After the next factory-side deploy:

- After a worker taps Finish, the kiosk keeps him off the live board
  for at least 5 minutes, regardless of how slow the cloud push is.
- If the cloud's `session_finish` push has consistently failed (a
  real push problem, not a race), the cloud view will eventually
  resurrect the worker after the tombstone TTL — surfacing the
  underlying issue rather than hiding it forever.
- A new `/api/cloud-refresh-health` field (`recentFinishTombstoneSize`)
  reports how many `emp_id`s are currently shielded from a stale-cloud-
  resurrection. A sustained non-zero count is a useful signal that the
  `session_finish` push is consistently failing.

**Zero factory-side changes.** This is purely a LAN-server-side fix.
The kiosk client doesn't change.

## 6. Future-proofing (deferred)

- **Cross-laptop tombstone.** A future v1.2.5x could push the tombstone
  to the cloud as a `recent_finish_tombstone` row keyed by `emp_id`,
  so other factory laptops honor it too. The current per-process
  in-memory tombstone covers the same-laptop case the user reported;
  the cross-laptop case is rarer (factory laptops usually don't share
  workers) and out of scope.
- **Persist tombstone across LAN-server restart.** A boot-time SQLite
  table (`tombstone_store`) could survive a reboot, but on reboot the
  LAN re-hydrates `ACTIVE_SESSIONS` from the offline-report snapshot
  anyway — so a tombstone that outlived a reboot would just hide
  genuinely-active workers. Per-process in-memory is the right
  default.
- **`active_sessions` cleanup at the factory boot.** The v1.2.31
  `dropGhostActiveSessions` handler runs at boot but only deletes
  rows with empty `emp_name` / `emp_code`. Pre-v1.2.44 LAN code can
  re-push ghosts between boot and dashboard render. The cloud-side
  scrub (v1.2.45) is the only complete fix until every factory picks
  up v1.2.43+.

## 7. What if the factory's `session_finish` push never reaches the cloud?

The 5-minute tombstone TTL will eventually expire. After that, the
cloud's stale `active_sessions` row for Arman will resurrect him on
the LAN — at which point the operator should see the resurrection
flash AND check the LAN's `/api/cloud-refresh-health` endpoint for a
sustained non-zero `recentFinishTombstoneSize`. That's the signal
that the cloud push is genuinely broken, and the operator should
investigate `/api/ceo-ingest-status` for the underlying push failures.

This is intentional behavior: the tombstone masks the symptom for 5
minutes; it does NOT hide the underlying problem forever. The operator
gets a clean kiosk during the normal race window, but a still-broken
push will still surface eventually.
