# v1.2.33 — Cloud dashboard blank-page regression fix + PM2/PnP factory recovery

## What's broken (and why)

Two bugs from v1.2.32 surfaced within hours of each other on
2026-09-13 / 2026-09-14:

1. **Cloud dashboard (`dashboard.farewellabaya.com`) shows a blank
   page with one JS error in the console** —
   `Uncaught SyntaxError: Invalid regular expression:
   /\/g, '\\').replace(/: Unmatched ')'`. Every `/ceo` page load failed
   to parse the inline `<script>` block, so the dashboard never
   rendered. The Worker bundle parsed fine (so `/api/state` was
   returning JSON — which masked the issue in our smoke tests, all of
   which exercise `/api/*` rather than `/ceo` HTML).

2. **PM2 factory server crashes on auto-update**, then refuses to
   restart — `pm2 list` shows `abaya-server` as `errored` /
   `stopped`. The factory's kiosk LAN dashboard is still up (the OS
   didn't kill the listening socket), but new sessions don't sync to
   the cloud because the push side is dead. This is the same root
   cause as the 2026-09-09 regression: PM2's ProcessContainerFork.js
   does `require('pm2-io-bpm')` at startup, and PnP rejects pm2's own
   deps because they're not in our `package.json`. v1.2.27 worked
   because PM2 was on PATH globally; v1.2.30+ broke when the ecosystem
   added `interpreter_args: ['-r', './.pnp.cjs']`.

Both bugs are **silent** from a smoke-test standpoint. v1.2.32's
`scripts/smoke-tickets.mjs` only checks `/api/*` endpoints — never
the rendered HTML — so the cloud dashboard went out broken even with
12/12 smoke tests green. PM2 was last verified working in v1.2.27
(see project memory); v1.2.32 didn't re-test it.

## Operational root cause of the cloud dashboard

`cloudflare/src/ui/ceo-pages.js` has **one** function exported at the
top level (`getCEODashboard`, line 105) and ~70 helper functions
defined later in the file. The `getCEODashboard` body is a single
giant JS template literal that spans **lines 108 → 4505** and contains
the entire rendered HTML — including the inline `<script>` block that
runs in the browser.

v1.2.32's 1Hz-tick refactor introduced `cssEscapeAttr()` at line 1620
to escape `emp_id` values for CSS attribute selectors. The function
was placed **inside the template-literal body** (because
`tickLiveSessions()` at line 1579 references it, and `tickLiveSessions`
is inside the template literal too). The author wrote:

```js
function cssEscapeAttr(s) {
  return String(s).replace(/\\/g, '\\\\').replace(/"/g, '\\"');
}
```

That's correct JS — `/\\/g` matches one backslash, `'\\\\'` is the
string containing two backslashes, etc. **But it lives inside a
template literal.** Template literals consume `\\` → `\` on output
the same way they consume `\`` → `` ` ``. So the rendered HTML had:

```js
return String(s).replace(/\/g, '\\').replace(/"/g, '\"');
```

The first regex is now `/\/g` (invalid — `\/` inside a regex means
"literal forward slash", then `/g` is the regex closing delimiter and
flag, then `, '\\').replace(/` follows). The browser's JS parser sees
this and throws `Invalid regular expression: /\/g, '\\').replace(/:
Unmatched ')'` on the very first line of the inline script. **The
entire `/ceo` HTML page fails to render.** The login page (`/ceo`
unauthenticated, served from `getLoginPage()`) is unaffected because
it's a different function with no template-literal corruption.

This is the **same class of bug** that bit v1.2.32 (the cloud 404
fix), but with a different mechanism: v1.2.32 was unescaped backticks
inside a template-literal comment; v1.2.33 is the template literal
eating the backslashes inside a regex literal. Both leave the rendered
inline script unparseable.

## Fix

### `cloudflare/src/ui/ceo-pages.js` — `cssEscapeAttr()` (line 1620)

Double every backslash inside the function body, because we live
inside the template literal:

```js
function cssEscapeAttr(s) {
  return String(s).replace(/\\\\/g, '\\\\\\\\').replace(/"/g, '\\\\"');
}
```

The function comment above explains the pattern and links it back to
v1.2.32's `escWA()` precedent (which already had to use the
double-escape trick). Future maintainers who add a regex/replacement
inside the template-literal body must apply the same pattern.

### `tests/dashboard-live-tick.test.mjs` — two new regression tests

1. `ceo-pages.js: every regex/replacement inside the
   getCEODashboard template literal escapes backslashes correctly` —
   source-level audit. Scans the template-literal body (lines
   108..4505) for every regex literal, ignores `// ...` and
   `/* ... */` comments, ignores HTML URL-ish false positives, and
   verifies that the pattern has an even number of "ordinary"
   backslashes (after stripping `\`` template-literal backtick
   escapes, which are a different beast). An odd count would mean a
   single trailing `\` before the regex closing `/` — exactly the
   v1.2.32 cssEscapeAttr corruption pattern.

2. `ceo-pages.js: rendered cssEscapeAttr() correctly escapes
   backslashes and quotes` — behavioral test. Renders the dashboard,
   locates the `function cssEscapeAttr(s) {` line in the rendered
   HTML, evals it via `new Function`, and asserts the actual escape
   output for plain / backslash / double-quote / mixed / empty /
   null inputs. If the regex is corrupted, `new Function` itself
   throws the same `Invalid regular expression: ...` error the
   browser saw, surfacing as a clean test failure with the exact
   parser message.

Both tests **fail on the pre-fix code** (test #2 fails with the
exact error the user reported in their browser console) and pass on
the post-fix code.

### `ecosystem.config.cjs` + `install/run-pm2.cjs` + `install/pm2-*-wrapper.{js,cmd}` — PM2 / PnP factory recovery

Replace the `interpreter_args: ['-r', './.pnp.cjs']` pattern (which
caused PM2's wrapper to crash on its own `pm2-io-bpm` require) with
a **plain-Node wrapper script**:

- `install/pm2-abaya-wrapper.js` — plain Node (no PnP, no pm2 deps).
  PM2's ProcessContainerFork launches it via its own wrapper, which
  can `require('pm2-io-bpm')` cleanly. THIS script then
  `spawn(NODE, ['-r', './.pnp.cjs', 'server.js'])` in a child
  process. PnP applies only to the factory code, where it belongs.
- `install/pm2-catalog-watcher-wrapper.js` — same pattern for the
  optional office-side watcher.
- `ecosystem.config.cjs` — `script: 'install\\pm2-abaya-wrapper.js'`,
  `interpreter: 'node'`, no `interpreter_args`. PM2 launches
  `node install/pm2-abaya-wrapper.js` cleanly, the wrapper does the
  PnP split.
- `install/run-pm2.cjs` — keeps the global-PM2 + strip-NODE_OPTIONS
  logic so anyone who runs `node -r ./.pnp.cjs install/run-pm2.cjs ...`
  still gets a working PM2 invocation.

The `.cmd` alternatives (`install/pm2-abaya-launcher.cmd`,
`install/pm2-catalog-watcher-launcher.cmd`) are kept as a fallback
for `pm2 start` invocations that go through a shell.

After this ships, factory PCs running the auto-update will pick up
the new ecosystem config. The PM2 process keeps running (no
auto-update triggers a restart of a running process), so the operator
needs to:

```
PM2-CMD.bat restart ecosystem.config.cjs
PM2-CMD.bat save
```

…or just reboot. After that, `pm2 list` shows `abaya-server`
`online` and `catalog-watcher` `online` (if the watcher was already
configured). The PM2 crash loop is over.

## Why v1.2.32's smoke tests didn't catch the dashboard blank page

`scripts/smoke-tickets.mjs` exercises 12 endpoints but **only
`/api/*`**. `/ceo` is touched in step 12 (which verifies the login
page loads), but the dashboard body — which lives behind the CEO
login and contains the broken inline script — is never rendered by
the smoke test. A future hardening should:

- Add a `node --check`-style parse on the rendered `/ceo` HTML's
  inline scripts (the new test #2 above catches the cssEscapeAttr
  regression, but only because the function's output ends up inside
  a JS-evaluable context).
- Optionally: spin up `wrangler dev --local`, render `/ceo` with a
  test CEO cookie, and assert no `console.error` events fire during
  page load.

## Migration

**Factory (auto-updates):** no operator action required for the
cloud dashboard fix. For the PM2 recovery, the operator needs to
restart the running PM2 process once (the auto-updater replaces the
files but does not bounce the running Node process):

```
PM2-CMD.bat restart ecosystem.config.cjs
PM2-CMD.bat save
```

After this, `pm2 list` shows `abaya-server` `online` and stays there
across reboots (via the OS-level pm2 startup that ships with the
launcher).

**Cloud:** zero action. Push to `main`, the Cloudflare Git
integration redeploys the Worker automatically. The smoke tests are
extended with the two new regression tests so a future backtick or
backslash mishap fails CI before it reaches the edge.
