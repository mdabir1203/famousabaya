# v1.2.24 — Support tickets inside the launcher

**Date:** 2026-09-05
**Status:** SHIPPED

## What this release does

A complete "factory → office" support channel inside the Electron launcher.
Operators can create a WhatsApp-bound ticket from the launcher's new
**Support** tab. The office gets the ticket on the configured phone
number with the details pre-filled. Replies appear in the launcher's
ticket detail view in real time. Everything is recorded in D1 (and
mirrored to the local SQLite snapshot) for audit + metrics.

Phase 1 (this release) is **wa.me send + manual-mark-resolved**:
operator creates, office replies on WhatsApp, operator marks resolved.
Phase 2 (next release) will add a `whatsapp-web.js` bot running on the
office PC to capture replies automatically and surface them in the
launcher via webhook — same data model, no schema change.

## What's new

### For factory operators
- **Support tab** in the launcher (`Support` button in the form column)
- Three-column layout: **New ticket** form, **Tickets** list with status
  filter (Open / Pending / Resolved / All), and **Ticket detail** with
  full event timeline + message thread
- Form fields: category (5 + Other), priority (normal / urgent),
  subject, description
- Operator id pre-fill (`e_bc_<digits>`) — saved to localStorage so the
  factory PC doesn't re-type every launch
- One-tap "Create & send via WhatsApp" — opens `wa.me/<office>?text=<ticket>`
  in the default browser; operator taps Send on their phone
- "Mark resolved" button on the detail view

### For office
- Receives the ticket on the configured WhatsApp number with:
  - First line: `[T-YYYY-MM-DD-XXXX] <subject>` (id is the first thing
    they see so they can quote it back)
  - Category + priority
  - Operator name + emp_id
  - Station (if known)
  - Free-form description
- One-tap resolve page at `https://dashboard.farewellabaya.com/r/<id>`
  — no login, no app, just a "Mark resolved" button
- Full ticket history view in the cloud dashboard (read-only; the CEO
  view shows the same data the launcher shows)

### Configurable office number
- Default in `install/.env.production.template`: `+971543618066`
- Overridable from the launcher's Support panel (writes to
  `worker_settings.support_office_numbers` in D1)
- Format: comma-separated E.164 numbers. First = primary, rest =
  fallbacks for Phase 3 escalation (auto-retry from fallback when
  primary doesn't reply in time)

## Architecture

### Data model (3 new tables, migration 0020)
```sql
CREATE TABLE tickets (
  id TEXT PRIMARY KEY NOT NULL,                    -- T-YYYY-MM-DD-XXXX
  created_at INTEGER NOT NULL,
  created_by TEXT NOT NULL,                          -- e_bc_<digits> (AGENTS.md rule #1)
  created_by_name TEXT,
  category TEXT NOT NULL,                            -- login|app|network|hardware|catalog|other
  priority TEXT NOT NULL DEFAULT 'normal',           -- normal|urgent
  subject TEXT NOT NULL,
  description TEXT NOT NULL,
  status TEXT NOT NULL DEFAULT 'open',               -- open|pending|resolved|closed
  resolved_at INTEGER, resolved_by TEXT,
  whatsapp_to TEXT,                                 -- E.164 of the office it was sent to
  escalated_at INTEGER, last_message_at INTEGER, station TEXT,
  updated_at INTEGER DEFAULT (unixepoch())
);
CREATE TABLE ticket_events (id, ticket_id, event, actor, at, note);
CREATE TABLE ticket_messages (id, ticket_id, direction, sender, text, via, wa_message_id, sent_at);
```

The local SQLite snapshot mirrors all three tables (per AGENTS.md rule #3).
A `BEFORE INSERT` trigger on the cloud `tickets` table rejects any row
whose `created_by` is not `e_bc_<digits>` — same pattern as `sessions`.

### Worker endpoints (v1.2.24)
| Endpoint | Method | Auth | Purpose |
|---|---|---|---|
| `/api/tickets` | POST | X-Ingest-Secret | Create |
| `/api/tickets` | GET | none | List (filters: status, category, priority, since, until) |
| `/api/tickets/:id` | GET | none | Detail with events + messages |
| `/api/tickets/:id/resolve` | POST | X-Ingest-Secret | Mark resolved |
| `/api/tickets/:id/reopen` | POST | X-Ingest-Secret | Reopen |
| `/api/tickets/:id/reply` | POST | X-Ingest-Secret | Operator-side reply (Phase 2) |
| `/r/:id` | GET | none | One-tap resolve page (HTML) |
| `/api/worker-settings/support` | GET / PUT | none / X-Ingest-Secret | Office number config |
| `/webhook/whatsapp-incoming` | POST | X-Bot-Secret | Bot → Worker (Phase 2) |

### Local server proxy (`server.js`)
- `POST /api/tickets` → proxies to cloud with `X-Ingest-Secret`
- `GET /api/tickets` → proxies to cloud (read, no auth)
- `GET /api/tickets/:id` → proxies to cloud
- `POST /api/tickets/:id/{resolve,reopen,reply}` → proxies to cloud
- `GET /api/worker-settings/support` → proxies
- `PUT /api/worker-settings/support` → proxies (with `X-Ingest-Secret`)

The renderer never talks to the cloud directly — it always goes through
the local server, which already has the right secret in `CF_INGEST_SECRET`.

### Electron renderer (`tools/desktop-launcher/`)
- **`support.js`** — the full Support tab module (render, fetch, render
  details, mark resolved). Pre-existing localStorage for the operator
  id. Color-coded status badges, priority pills, time-ago timestamps.
- **`preload.js`** — exposed `getApiBaseUrl`, `apiFetch`, `openExternal`
  on `window.abayaLauncher` so `support.js` doesn't need to know about
  the local server's port.
- **`main.js`** — added `ipcMain.handle('get-api-base-url')` and
  `ipcMain.handle('api-fetch')` handlers. The api-fetch handler
  forwards the `X-Ingest-Secret` automatically for write requests.
- **`index.html`** — added `#supportMount` container, the support
  styles, and a `<script src='support.js'></script>` tag.

## What's NOT in this release (deliberate)

- **Phase 2 — whatsapp-web.js bot for two-way replies.** The webhook
  endpoint is in place and tested; the bot itself is a separate tool
  (`tools/whatsapp-bot/`) that lives on the office PC. Phase 2 ships
  as soon as the office PC is ready.
- **Primary → fallback escalation timer.** The data model supports it
  (`escalated_at` column, list of office numbers in
  `worker_settings.support_office_numbers`), but the cron/handler
  that auto-escalates after X minutes is Phase 3.
- **Local-side ticket mirror on the launcher's home dashboard.** Today
  the launcher reads from D1 via the local server proxy. A local
  mirror in the snapshot's existing pattern (read-on-boot, periodic
  refresh) is a nice-to-have for offline-resilience but not blocking.
- **In-app reply box.** Operator can mark resolved, but sending a
  reply currently requires the office bot (Phase 2). When Phase 2
  lands, support.js will gain a reply box that hits
  `POST /api/tickets/:id/reply` → Worker → bot → WhatsApp.

## Rollback

If v1.2.24 has a problem, `gh release download v1.2.23` and install
manually. The Support tab is a new addition — rolling back doesn't
break any existing functionality. The D1 tables stay (migration 0020
is additive: `CREATE TABLE IF NOT EXISTS`), so a future re-deploy of
v1.2.24 will work against the same DB.
