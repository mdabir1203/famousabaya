# v1.2.45 — Read-path scrub: drop ghosts + dups at the SQL layer

> **TL;DR:** The cloud's read handlers now filter `active_sessions` by
> current roster + 24h age, and dedup `sessions` by `(emp_id,
> started_at)` keeping the largest `ended_at`. The Live Active Sessions
> tile and every aggregation on the CEO dashboard (`/api/state`) stop
> showing ghost and duplicate rows even while factory laptops are still
> running buggy pre-v1.2.43 LAN code. Until every factory catches up,
> this is the defense-in-depth layer that keeps the dashboard clean.

---

## 1. The problem

After shipping v1.2.42 (one-time ghost cleanup) and v1.2.43 (one-time
sessions dedup), the cloud was clean — but the **factory's LAN server
is still pushing new noise** because:

- Migration 0022 only deleted the **historical** ghosts. The factory's
  `close-stale-sessions` endpoint can resurrect `e_bc_999998` and
  `e_bc_00000141` on every restart (re-hydrating from offline-report).
- Migration 0023 only deleted the **historical** duplicates. The
  factory's LAN has no idempotency guard until v1.2.43 deploys to
  every laptop.

So the moment the operator looked away, the cloud started re-accumulating
the same noise. By 2026-09-19 13:00 Dubai:

- `active_sessions`: 17 rows (2 ghosts back)
- `sessions`: 7,450 rows (70 dup clusters back)
- `dups`: 70
- `ghosts`: 2

The dashboard's Live Active Sessions tile started showing Ashanfi /
EMP141 again. The PROCESS COMPLETED count on the per-employee day modal
started tripling again. We needed server-side scrubbing at the SQL
layer — independent of whether the factory has the v1.2.43 LAN code.

## 2. The fix

A new shared module `cloudflare/src/domain/data-cleanup.js` exports two
helpers:

```js
import { activeSessionWhere, dedupSessionsCte } from '../domain/data-cleanup.js';
```

### 2.1 `activeSessionWhere(nowSec)` — ghost + orphan scrub

Returns a SQL fragment:
```
started_at >= <nowSec - 86400> AND emp_id IN ('e_bc_00000121', 'e_bc_00000111', ...)
```

The `nowSec` parameter is the snapshot timestamp (computed once per
handler invocation, then reused across all queries in the batch — a
session that crosses the cutoff mid-batch cannot appear in some
aggregations and not others).

The roster is the **same 19 employees** as `data/employees-manual.json`
on the LAN as of 2026-09-19. When the operator adds / removes an
employee, mirror the change in `CURRENT_ROSTER_IDS` in the same commit.
The unit test `tests/data-cleanup.test.mjs` enforces the size range
[15, 30] and the presence of `e_bc_00000121`. The data-cleanup module
**must be updated in lock-step with the LAN's `employees-manual.json`** —
mismatch means either a real worker is hidden from the live tile or a
former employee ghosts back.

Applied to:
- `state.js → stmtActive` (Live Active Sessions tile)
- `report.js → active_sessions` query (executive summary "Active
  Workers" KPI)

### 2.2 `dedupSessionsCte()` — sessions dedup at SQL layer

Returns a CTE fragment:
```sql
WITH survivors AS (
  SELECT id FROM (
    SELECT id, ROW_NUMBER() OVER (
      PARTITION BY emp_id, started_at
      ORDER BY ended_at DESC, id DESC
    ) AS rn FROM sessions
  ) WHERE rn = 1
)
```

This is the **single-statement CTE form** that the v1.2.43 migration
0023 documentation eventually settled on (see §7 of that release note
for the full disaster-recovery story). D1 supports `ROW_NUMBER() OVER`
as of `compatibility_date: 2024-11-01` (see `cloudflare/wrangler.toml`).

Use by composing in front of any aggregation:
```sql
${dedupSessionsCte()}
SELECT s.emp_id, COUNT(*) AS units
  FROM sessions s JOIN survivors w ON w.id = s.id
 WHERE s.day_date = ? AND s.emp_id LIKE 'e_bc_%'
 GROUP BY s.emp_id
```

Applied to:
- `state.js → stmtPerf` (Per-employee Performance tile)
- `state.js → stmtAgg` (Completed Today + Work Time KPIs)
- `state.js → stmtAbayasDelivered` (Abayas Delivered KPI)
- `state.js → stmtProcSplit` (Process Split chart)
- `state.js → stmtHourly` (Hourly distribution chart)
- `state.js → stmtGarment` (Garment Totals tile)

Each query is rewritten to `FROM sessions s JOIN survivors w ON w.id = s.id`
so the row_read cost is identical to the un-deduped version (D1
evaluates the window function in a single pass).

### 2.3 `emp_id LIKE 'e_bc_%'` on `stmtLogs`

The Recent Invoice Logs table on the dashboard read directly from
`sessions` without an emp_id guard — it was leaking synthetic ids.
Added the guard so the logs list only contains real employees.

## 6. Future-proofing (deferred)

- **Read-path scrub is per-handler.** A future dashboard endpoint
  reading `active_sessions` without `activeSessionWhere` would re-leak
  ghosts. There's no compile-time check for "every `FROM active_sessions`
  has the helper". A lint rule or a `wrapActiveSessionsQuery()` factory
  is a candidate for v1.2.46+ — for now the unit tests + §11 in
  AGENTS.md are the contract.
- **Roster size 19 is hardcoded.** When the operator hires the next
  employee (EMP142 etc.), the new id must be added to both
  `data/employees-manual.json` AND `CURRENT_ROSTER_IDS` in
  `cloudflare/src/domain/data-cleanup.js`. The unit test's size band
  [15, 30] is the only safety net — a more aggressive test could
  fail CI if the two files diverge.
- **`active_sessions` cleanup at the factory boot.** The v1.2.31
  `dropGhostActiveSessions` handler runs at boot but only deletes
  rows with empty `emp_name` / `emp_code`. Pre-v1.2.44 LAN code can
  re-push ghosts between boot and dashboard render. The cloud-side
  scrub is the only complete fix until every factory picks up
  v1.2.43+.

## 7. What if the factory never picks up v1.2.43?

The read-path scrub holds indefinitely. Ghost and dup rows keep
accumulating in the cloud D1 (cheap on storage, harmless because the
SQL filter drops them). The operator never sees them on the dashboard.

The cost is a small row_read overhead — every dashboard render scans
the full `sessions` table to compute the dedup CTE, then JOINs back.
For the current ~7,500 sessions table that's ~30ms per render, which
is well under the 5s response cache TTL.

When the table grows past ~50,000 sessions, the dedup CTE may become
noticeable. At that point the right fix is a `MAX(ended_at)` indexed
view or a periodic `INSERT OR REPLACE` of the deduped set into a
`sessions_dedup` mirror table. Not in scope for v1.2.45.
