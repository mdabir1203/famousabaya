# v1.2.27 — D1 graceful degradation + observability

> **Released:** 2026-09-07
> **Severity:** Hardening (lessons from the v1.2.26 500-storm)
> **Scope:** Cloudflare Worker only — no install/launcher change required
> **Tag:** `v1.2.27`

## TL;DR

The Worker used to return generic `500 Internal Server Error` whenever D1
hiccupped (quota, network, internal). That made it impossible to
distinguish "retry me in 30s" from "you have a bug". This release maps
D1 errors to **`503 Service Unavailable` with `Retry-After: 30`** and
adds an explicit `/api/d1-health` probe for the CEO dashboard's
"data is stale" banner. Factory server's local queue already treats
5xx as transient, so the upgrade is now correctly classified as
retry-not-permanent.

## What changed

### `cloudflare/src/http-response.js`

Two new helpers exported:

```js
isD1Error(err)
  // → true for any error whose .message starts with 'D1_ERROR:'

d1ErrorResponse(err, retryAfterSec = 30)
  // → 503 Response with shape { ok: false, error: 'database ...' }
  //   and 'Retry-After: 30' header
```

`errRes` is now signature-compatible with `jsonRes` (accepts an
`extraHeaders` argument) so it can attach the `Retry-After` header
when needed.

### `cloudflare/src/index.js`

1. The top-level `catch` now checks `isD1Error(e)` first. If yes, it
   returns 503 with `Retry-After: 30`. If not, it falls back to the
   existing 500. The factory server's `pushToCloudflare` already
   treats 5xx as transient and queues the payload to disk for retry,
   so this changes "queued for permanent failure" → "queued for retry".

2. New open endpoint: **`GET /api/d1-health`** does a single
   `SELECT 1 as ok` against D1 and returns:
   - 200 `{ ok: true, d1: 'healthy' }` on success
   - 503 `{ ok: false, error: 'database temporarily unavailable...' }`
     with `Retry-After: 10` on D1 failure
   - 500 on any other error

   It's exempted from the CEO-auth gate (just like `/api/health` and
   `/api/tickets`) because both the factory server and the dashboard's
   "stale data" banner want to poll it without a CEO cookie. It only
   does a 1-row read, so it can't leak sensitive data.

### `cloudflare/src/handlers/state.js`

Cache-hit responses now include a `_cache` field:

```json
{
  "_cache": { "hit": true, "age_ms": 2340, "age_sec": 2 },
  ...
}
```

This lets the CEO dashboard render a "data is Ns old" banner when D1
is struggling and the cache is doing the heavy lifting. Without this,
the operator can't distinguish "live" from "stale" from "broken".

### Tests

- **`tests/d1-graceful-degradation.test.mjs`** (new, 5 cases): pins

- **`tests/state-cache.test.mjs`** (updated, +1 assertion): the cache

- **`scripts/smoke-tickets.mjs`** (updated, +1 step): new step 10

## Why this matters

The v1.2.26 incident (D1 free-tier limit hit → 9h of silent factory
data loss) had three root causes that this release addresses:

1. **All Worker errors looked the same.** The factory server's
   `pushToCloudflare` couldn't tell apart "D1 is overloaded" from
   "your code has a bug". The first should retry; the second should
   page someone. `isD1Error` makes that distinction explicit.

2. **No visibility into D1 health.** Operators had no way to know
   "D1 is the problem, not the Worker". `/api/d1-health` is the
   single, low-cardinality probe that answers that question in one
   HTTP call.

3. **No staleness signal.** During the 5s cache window, the
   dashboard would happily show "live" data that was actually 5s
   stale and served from memory. The new `_cache` field gives the
   UI a single number to render in a banner.

## Operator-visible effects

**Before v1.2.27:**
- D1 hiccup → `POST /api/event` returns 500
- Factory server logs `[CF] Push failed (queued for retry)` and keeps
  retrying every 30s
- CEO dashboard sees 500 → "Service unavailable" message

**After v1.2.27:**
- D1 hiccup → `POST /api/event` returns 503 with `Retry-After: 30`
- Factory server logs the same retry queue message, but now the
  status code clearly signals "this is recoverable, back off"
- CEO dashboard can poll `/api/d1-health` to distinguish "Worker is
  down" from "D1 is slow" and show the right banner
- Cache hits carry `_cache: { hit: true, age_sec: N }` so the
  dashboard can show "data is Ns old" when D1 is being slow

## Follow-ups (deferred)

- **Telemetry on D1 quota**: a `cloudflare/quota` endpoint that
  reads the D1 metrics and exposes them as JSON. Useful for an
  "approaching limit" warning before the next outage. Not
  blocker for v1.2.27.
- **Dashboard banner UI**: the CEO dashboard's `ceo-pages.js`
  should consume the new `_cache` field. Out of scope for the
  Worker-only release.
- **State cache TTL bump**: 5s is fine for the current dashboard
  polling cadence, but if we go to 30s+ we save a lot more reads.
  Holding for telemetry.
