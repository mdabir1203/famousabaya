# v1.2.40 — Realtime sub-second lane + factory/cloud watermark

> **TL;DR:** The cloud CEO dashboard now reflects factory-floor Start/Finish
> events within **~300 ms end-to-end** (terminal tap → cloud D1 write → SSE
> broadcast → browser paint) instead of being bounded by the previous 1 s
> `/api/state` poll. A monotonic `local_seq` watermark on every push
> lets the operator see, in one glance, whether the LAN and cloud views
> agree — same data on both dashboards, no drift, no surprises.
>
> No new Cloudflare billable surface (no Durable Object — the SSE
> fan-out runs in the existing Worker's module-scoped state). The factory
> server doesn't change its push cadence, only its payload. The
> migration adds one D1 row.
>
> **Sub-second target met.** Same-data guarantee visible at all times.

---

## 1. What changed

### 1.1 Factory server — `local_seq` watermark on every push

Every `pushToCloudflare(type, payload)` call now stamps the payload with
`local_seq: <monotonic int>` before it leaves the box. The counter is
per-process-lifetime (resets on restart; cloud handles replays
idempotently because of the MAX() UPSERT).

- **Outbound path** (`server.js:pushToCloudflare`):
  - `seq = ++factoryLocalSeq`
  - `enriched = Object.assign({}, payload, { local_seq: seq })`
  - 2xx → `factoryLastPushedSeq = MAX(current, seq)`
  - Permanent 4xx (roster reject) → also bumps the watermark (the cloud
    *saw* the event; the LAN knows it's been received even if not
    persisted). Without this the "factory ahead" drift counter would
    falsely claim N pending events forever.
  - Auth 401/403 → goes to NDJSON retry queue; watermark NOT bumped
    (the cloud didn't see it because auth failed).
  - Transient / network failure → goes to retry queue; watermark NOT
    bumped.

- **Replay path** (`server.js:drainCeoIngestQueue`): every successful
  replay bumps the watermark from the payload's stored `local_seq`. NDJSON
  records carry the seq so replays carry the original id; no re-stamp.

- **Liveness endpoint** (`GET /api/ceo-ingest-status`):
  ```json
  "sync": {
    "localSeq": 1418,
    "lastPushedSeq": 1418,
    "lastQueuedSeq": 1418,
    "lastSeqPushedAt": 1789492982000,
    "inFlight": 0,
    "queued": 0,
    "mode": "cloud-live",
    "lagSeq": 0,
    "eventsEmittedThisSession": 1418
  }
  ```
  Operators comparing LAN and cloud can read both `localSeq` (factory)
  and `state_meta.factory_seq_max_received` (cloud) and confirm they
  match.

### 1.2 Cloud Worker — `factory_sync` watermark + SSE lane

- **Migration `0021_factory_sync_watermark.sql`** — single-row table
  tracking the highest `local_seq` the cloud has received. The PK is
  `(seq_type)` so future watermarks (catalog, roster) can coexist.

  ```sql
  CREATE TABLE IF NOT EXISTS factory_sync (
    seq_type        TEXT    PRIMARY KEY,
    seq_value       INTEGER NOT NULL DEFAULT 0,
    last_event_type TEXT,
    last_emp_id     TEXT,
    updated_at      INTEGER NOT NULL DEFAULT (unixepoch())
  );
  ```

  Local snapshot mirrors it per AGENTS.md rule #3
  (`shared/sqlite-snapshot.cjs` → SCHEMA_DDL).

- **Ingest path** (`cloudflare/src/handlers/ingest.js`):
  - `updateFactorySeqWatermark()` UPSERTs `factory_sync` after every
    successful D1 write. Uses
    `seq_value = MAX(factory_sync.seq_value, excluded.seq_value)` so a
    queue replay that delivers an older seq is a no-op.
  - Returns the new `seq_value` to the LAN via the JSON response body
    (so the LAN can track its own high watermark).
  - Tolerates missing/non-finite `local_seq` (legacy factory servers
    keep working unchanged).
  - On success broadcasts the event to every open SSE connection.

- **`/api/state`** — the response now carries:
  ```json
  "state_meta": {
    "factory_seq_max_received": 1418,
    "factory_seq_last_received_at": 1789492982,
    "factory_seq_last_event_type": "session_finish",
    "factory_seq_last_emp_id": "e_bc_00000110"
  }
  ```
  `/api/state` reads the watermark once per call (extra `.first()`),
  so the cache behavior is unchanged. Negligible row_read impact.

- **New endpoint `GET /api/realtime/sse`** —
  Server-Sent Events stream. Module-scoped fan-out: every browser
  connected to the dashboard gets the same JSON event within the same
  isolate. Worker streaming responses stay open as long as the runtime
  has CPU budget; on isolate eviction the browser's `EventSource` API
  auto-reconnects and the next `/api/state` poll re-hydrates state.
  Heartbeat `:keep-alive` every 15 s prevents middlebox idle-kill.

  Why not Durable Objects?
  > DO billing (~$0.15/M req min) for no functional gain — the simple
  > per-isolate fan-out plus auto-reconnect works, and we already accept
  > isolate eviction for the in-memory response cache (`state.js`).

- **`GET /api/realtime/sse/stats`** — ops visibility
  (`{ connected, totalJoins, totalBroadcasts, totalDropped, ... }`).

### 1.3 Cloud CEO dashboard — sub-second SSE consumer + RT pill

`cloudflare/src/ui/ceo-pages.js`:

- `openRealtimeSse()` opens `new EventSource('/api/realtime/sse')` on
  load (alongside the existing 1-4.5 s `/api/state` poll).
- `onRealtimeEvent(ev)` applies the diff in place:
  - **`session_start`**: insert/update `STATE.active[emp_id]` placeholder.
  - **`session_finish`**: delete from `STATE.active[emp_id]`, increment
    `STATE.completed_today`, increment the relevant
    `STATE.process_split_today[process]` bucket.
- Bumps `_lastStateHash` reset so `renderAll()` runs and the diff shows
  up immediately. The full reflow (rows, perf, garment totals, abaya
  builds) still needs the next `/api/state` poll — the SSE patch just
  makes the first paint within ~300 ms rather than ~1000 ms.
- **`FACTORY SYNC` pill** next to the existing LIVE badge:
  - `live` (green): SSE connected AND cloud seq updated < 30 s ago.
  - `warm` (amber): stream alive but no commit in 30 s – 5 min.
  - `stale` (red): ≥ 5 min of silence on the watermark — operator
    action item.
  - `idle` (grey): SSE not connected (browser too old, `/api/realtime/sse`
    blocked, etc.). Fallback to the 1 s poll still works.

### 1.4 LAN dashboard — no change

The LAN dashboard's `STATE` is the factory server's authoritative
in-memory state (Socket.IO `state_update` events on every Start/Finish
taps within < 100 ms). It was already realtime. The watermark is
exposed via `/api/ceo-ingest-status.sync` for any launcher UI to read.

## 2. End-to-end behavior (what the operator sees)

### Scenario A: happy shift, factory + cloud both online

1. Worker taps Start on terminal at `T`.
2. LAN server emits `socket.state_update` → LAN dashboard paints the row
   inside 100 ms.
3. LAN server `pushToCloudflare('session_start', { ... local_seq: 1419 })`
   posts to `/api/event`. 8 s timeout, fires immediately.
4. Cloud Worker ingests → D1 `active_sessions` REPLACE → broadcasts on
   SSE → every connected dashboard's `EventSource.onmessage` fires →
   `STATE.active[e_bc_00000110]` populated → `renderAll()` paints the
   row. Total: **~200–400 ms**.
5. `/api/state` returns (1 s poll) with the new row + the new watermark
   `factory_seq_max_received: 1419`.
6. Operator compares: LAN `localSeq = 1419`, cloud received `1419`.
   `FACTORY SYNC` pill stays green.

### Scenario B: factory has no internet for 30 seconds

1. Five Start/Finish events queue locally. `local_seq` 1420..1424.
2. LAN dashboard shows the events in < 100 ms as usual.
3. Cloud dashboard's last seq stays at 1419; `FACTORY SYNC` pill turns
   amber after 30 s, red after 5 min.
4. Connectivity restored. LAN queue replays; each replay's `local_seq`
   matches what the LAN already has, so the cloud's watermark bumps
   from 1419 to 1424 idempotently via `MAX(...)`.
5. Cloud dashboard next poll shows seq = 1424. SSE broadcasts the
   five queued events as they replay (sub-second from each `/api/event`
   200). SSE consumers update STATE for each.
6. `FACTORY SYNC` pill returns to green.

### Scenario C: roster reject (permanent 4xx)

1. Worker with a synthetic id (`e1` instead of `e_bc_*`) taps Start.
2. Cloud returns 422 with a clear "emp_id must be in the form e_bc_<barcode>"
   error.
3. Cloud `factory_sync` watermark IS bumped to 1425 (cloud saw the
   payload even though it rejected it).
4. LAN marks `pushPermanentRejected += 1`. `seq 1425` shows up in the
   rejected-queue file. No retry.
5. Cloud dashboard's `FACTORY SYNC` stays green. LAN's
   `/api/ceo-ingest-status.sync.lastPushedSeq` advances to 1425.
6. The mismatch is visible: the LAN dashboard never showed the worker
   on the live board in the first place (roster guard on the LAN side,
   AGENTS.md rule #1).

### Scenario D: Isolate eviction mid-shift

1. Cloud isolate evicts; all open SSE streams close.
2. Browser `EventSource` fires `error`; the consumer immediately calls
   `poll(true)` to re-hydrate STATE via `/api/state?live=1`.
3. Browser auto-reconnects SSE on `error` (per the spec). The next
   isolate accepts the connection; subsequent events broadcast normally.
4. Worst case: < 1 s gap of un-pushed events (the same window the
   `/api/state` poll provided anyway — purely additive).

## 5. Operator action items

None for the factory PC side. The OTA update is what runs the change.
On the cloud side the new migration auto-applies on next `wrangler
deploy` (the worker D1 migrations apply lazily on first run, per the
existing pattern; the migration is idempotent so re-running is safe).

If `wrangler d1 execute` is the deployment path instead, run:

```bash
cd cloudflare
npx wrangler d1 execute abaya-db --file=migrations/0021_factory_sync_watermark.sql --remote
```

Then redeploy the Worker:

```bash
npx wrangler deploy
```

## 6. What's still NOT in v1.2.40 (deferred)

- **Durable-Object-backed cross-isolate fan-out** — not needed. The
  per-isolate SSE set + auto-reconnect covers the use case without
  paying DO minutes. If we later see isolate-eviction frequency
  hurting UX, this is the lever.
- **Two-way state mirror (LAN sync FROM cloud)** — the dashboard's
  `/api/state?days=400` is the existing one-way pull. Not needed yet;
  the LAN dashboard already has its own state via Socket.IO.
- **Cloud dashboard SSE-driven per-build / per-abaya reflow** —
  currently the SSE patch only mutates active rows / completed count;
  the row reflow comes from the next `/api/state` poll (≤ 1 s).
  Two reasons not to ship full SSE-driven reflow: (a) the build CTE
  is expensive to recompute per-event, (b) sub-second is good enough
  for the operator's mental model.
- **Auto-restart on isolate eviction** — Cloudflare's runtime owns
  this; we can't influence it.
