# v1.2.32 — Live Active Session Counter Ticks Per Second (Cloud + Offline)

## Operational root cause of the "cloud is 404ing" symptom

When the v1.2.32 changes to `cloudflare/src/ui/ceo-pages.js` were first
drafted, three new comments referenced the helper name
`\`elapsedSinceStateSec\`` in markdown-style backticks. The file's
`getCEODashboard()` function returns a giant JavaScript template literal
spanning ~4,000 lines, and inside a template literal **`//` is NOT a
comment** — it's two literal characters in the output HTML. The
unescaped backticks therefore closed the template literal prematurely,
leaving the rest of the file to be parsed as code. The result: the
entire Worker bundle failed to parse, and **every route — including
`/api/state` — returned 404** to the dashboard.

This is a v1.2.32-specific regression caused by the comments inside the
template literal body, NOT by anything in the routing layer. The
factory-side `dashboard.js` was unaffected (no template literals
wrapping the file), so the LAN dashboard continued to work — which is
why the operator saw a fully populated offline dashboard and a 404 on
the cloud at the same time.

**Fix:** escaped the three backticks inside the template literal
(`\``) and added a `node --check` regression test in
`tests/dashboard-live-tick.test.mjs` so any future unescaped backtick
inside `getCEODashboard()` / `getLoginPage()` /
`getPrivacyPolicyPage()` / `getTermsOfServicePage()` fails CI before
it can ship and break the Worker bundle.

If the factory operator is still seeing a 404 on `dashboard.farewellabaya.com`
after this v1.2.32 lands, the fix is to redeploy the Worker:

```
npx wrangler deploy --config wrangler.jsonc
```

…or push the new commit to `main` (the Git integration picks it up
automatically). The previous bundle is still on the Cloudflare edge
serving 404s; a fresh deploy replaces it with the now-parsing bundle.

## Summary

The live "active today" and "this build" counters on both dashboards now
tick **every second** instead of every minute. Before this fix, the
displayed text snapped to `:00` seconds and only changed when crossing a
minute boundary, which made the counter look frozen between minutes. The
operator on the factory TV and the CEO on dashboard.farewellabaya.com
both saw the same staleness.

The underlying walk was a minute-by-minute in-shift re-walk (60s / 600s /
3600s steps) — accurate but visually frozen. The fix uses a **base + live**
formula:

- **base** = in-shift elapsed from session start to STATE arrival,
  computed once per state_update and memoized.
- **live** = `min(30, browserMs − STATE.ts)` seconds added each second, if
  currently in a shift window.

Same shape on both dashboards so the CEO's cloud view and the factory's
LAN view show the same number for the same session.

## What changed

### `cloudflare/src/ui/ceo-pages.js`

Three additions:

1. `computeThisBuildBaseCache()` — per-session in-shift walk snapshotted
   at STATE arrival, memoized on `STATE.ts` + the sorted active-id list +
   a "wh present" sentinel. Recomputes only when STATE changes.
2. `thisBuildSecondsFor(empId)` — base + live resolver used by both
   `buildLiveSessionsHtml()` (the initial render) and the new 1Hz
   `tickLiveSessions()`.
3. `tickLiveSessions()` — mirrors `public/dashboard.js`'s tick. Walks the
   `#live-sessions` rows, queries `[data-tick="active-today"]` and
   `[data-tick="build"]` per emp_id, and writes the new HMS string via
   `textContent`. Preserves any trailing "Custom" pill span inside the
   build cell. Scheduled via `setInterval(..., 1000)` next to the existing
   schedulePollLoop(), with a `visibilityState === 'hidden'` short-circuit
   and a try/catch so a tick error can never break the page.

The cloud's live cells now carry `data-tick="active-today"` /
`data-tick="build"` attributes (and `data-emp-id`) so the tick can find
them — same attribute contract as `public/dashboard.js`.

### `public/dashboard.js` — tickLiveSessions refactor

The existing `tickLiveSessions()` re-ran `computeInShiftSec()` and
`computeActiveTodaySec()` every second. Both walk minute-by-minute, so
the displayed text only changed when crossing a minute boundary. The fix:

- `computeLiveBaseCache()` — memoized snapshot of the two walks at
  STATE arrival, keyed on `STATE.generated_at` + the sorted active-id
  list.
- `tickLiveSessions()` reads from that cache and adds the live
  contribution. The "this build" cell's "Custom" pill is preserved by
  splitting `textContent` into leading-HMS + pill-suffix and rewriting
  only the leading part when the value changes.

### `tests/dashboard-live-tick.test.mjs` — two new regression tests

1. `dashboard.js tickLiveSessions uses base+live formula (ticks every
   second)` — source-level guard that `computeLiveBaseCache()` exists,
   reads `_liveBaseCache`, and the tick applies the
   `min(30, (browserMs - snapshotMs) / 1000)` live cap.
2. `ceo-pages.js (cloud) adds data-tick and 1Hz tickLiveSessions` —
   source-level guard that the cloud dashboard now emits both
   `data-tick` attributes, defines `tickLiveSessions()`,
   `thisBuildSecondsFor()`, and `computeThisBuildBaseCache()`, and
   schedules `setInterval(..., tickLiveSessions, 1000)`.

All 8 tests in the file pass; the 6 pre-existing tests still pass.

## Why the bug stayed hidden for so long

Both dashboards have always polled STATE frequently (1 Hz on the cloud
when there are active sessions, every state_update on the LAN), so the
DOM was being updated frequently. The update just produced visually
identical text — `:00` seconds stays `:00` until a minute boundary. An
operator who watched the counter for 30 seconds saw "54m 0s" → "54m 0s"
→ ... → "55m 0s" and read it as "the timer is broken / not realtime".

The minute-by-minute walk was a deliberate performance choice from
v1.2.19 (see `ceo-pages.js:1311-1318`) — 1,440 iterations for a 24h
forgotten-Finish session was unacceptable for a per-render walk. The
fix preserves that performance: the base walk happens once per
state_update (not per second), and the live contribution is just an
addition of `(browserMs - STATE.ts) / 1000` capped at 30.

## Sync root cause — investigation notes

While investigating, I confirmed the local server's
`pushToCloudflare('session_start', ...)` payload does **not** include
`effective_started_at`, `windowed_elapsed_sec`, `outside_shift`, or
`is_cross_day` (see `server.js:2279-2284`). The cloud's ingest handler
falls back to defaults (`payload.started_at || now`, `0`, `0`, `0`) and
then recomputes `windowed_elapsed_sec` at read time using the cloud's
working_hours config.

This is **not** a sync divergence in practice because the local server
refreshes its working_hours from the cloud every 5 min
(`server.js:4522-4523`), so the two configs agree. The cloud's
in-shift recomputation therefore matches what the local would have
pushed. No fix needed in this release — but if the two configs ever
drift, the cloud will silently show different numbers than the local.
A future hardening could push the live-state fields from the local
explicitly so the cloud never has to recompute.

## Migration

No factory-side action required. The fix is dashboard-only. After
updating to v1.2.32:

- Open `dashboard.farewellabaya.com` or `localhost:3111/dashboard` in
  any browser tab. The "active today" and "this build" counters visibly
  advance every second.
- Cross-day sessions still reset at factory-TZ midnight (the base
  walk uses the same `computeActiveTodaySec` cross-day clamp that was
  there before).
- The 30s live cap means a stale tab (no network for >30 s) won't
  accumulate wild drift; the next successful poll refreshes the
  snapshot.
