# v1.2.52 — Three more "LAN-local-vs-cloud-stale" guards + boot-hydrate local-overlay

> **TL;DR:** v1.2.51 defended `ACTIVE_SESSIONS` against the LAN mutating
> locally while the cloud pull reverts. v1.2.52 extends the same defense
> to the three other cloud-LAN sync paths the operator hits every day:
> the catalog pull (every 60 s), the employees pull (every 60 s), and
> the work-types pull (every 60 s). It also adds a **local-overlay
> merge** to the boot-time `hydrateCompletedLogsFromCloud` so a worker
> Finish tap during the 5-30 s `/api/state/history` round-trip doesn't
> get overwritten by the cloud's stale view. Together these close the
> other three doors of the same bug class.

---

## 1. The bug

### 1.1 The pattern, generalized

The v1.2.51 release notes documented the **Arman Reza resurrection**:
LAN mutates locally at T0, push leaves at T1, cloud pull runs at T2
(T1 < T2 < T3 = push lands), LAN state gets overwritten by cloud's
stale view at T2, kiosk shows stale state until the push eventually
clears the cloud row.

The same class of bug exists in four other places. The operator has
been hitting these regularly:

| Where | What the operator saw |
|---|---|
| **Catalog** (`refreshAbayaCatalogFromCloud`, every 60 s) | Operator marks `abaya_id 3439` as `is_custom = 1` in the LAN. ~30 s later, the cloud pull runs and overwrites it with the cloud's stale `is_custom = 0`. The "Custom" pill vanishes from the dashboard. |
| **Employees** (`refreshEmployeesFromCloud`, every 60 s) | Operator adds a new employee via the kiosk PUT. ~30 s later the cloud pull reverts it (or worse: drops the rename of an existing employee). |
| **Work types** (`refreshWorkTypesFromCloud`, every 60 s) | Operator adds "Stone Work" to the work-types list via `/api/admin/work-types`. The 60 s pull reverts it because the LAN→cloud push hasn't landed yet. |
| **Boot hydrate** (`hydrateCompletedLogsFromCloud`, 5-30 s round-trip) | Laptop reboots. The boot-time `/api/state/history` fetch takes 30 s on a slow network. During that 30 s, a worker taps Finish at the kiosk. The hydrate overwrites `COMPLETED_LOGS = hydrated` and the local Finish row is gone. Operator sees "this morning's first session is missing." |

### 1.2 The root cause class

All four are the same race: **LAN mutates locally, push is in flight,
cloud→LAN pull races past the push and overwrites the LAN with the
cloud's stale view.** v1.2.51's recent-finish tombstone was one
defense; v1.2.52 closes the other three doors of the same bug.

### 1.3 The data

Reproducible on any factory laptop: trigger a catalog edit (or any of
the four mutation types), watch the operator's change vanish within 60 s
(or right after the boot hydrate completes, in the boot case).

Pre-v1.2.52 boot hydrate is the most damaging: a 30 s boot-time race
loses 1-N rows per reboot, silently. Operators reported "the first
morning session is missing after every restart."

---

## 2. The fix

Two new shared helpers + a guard at every pull site:

### 2.1 `shared/recent-mutation-tombstone.cjs` — resource-level tombstone

The v1.2.51 helper `shared/recent-finish-tombstone.cjs` is keyed by
`emp_id` (per-Finish TTL). The new sibling `shared/recent-mutation-tombstone.cjs`
is global per-resource (single timestamp) and is used by the
catalog/employees/work-types pulls. Same TTL shape, same default
(30 s; configurable via `RECENT_CATALOG_MUTATION_TOMBSTONE_MS`,
`RECENT_EMPLOYEES_MUTATION_TOMBSTONE_MS`,
`RECENT_WORK_TYPES_MUTATION_TOMBSTONE_MS`), same in-memory / per-process
scope, same floor (5 s).

```js
const tomb = makeRecentMutationTombstone({ ttlMs: 30_000 });
tomb.note();              // local just mutated — start the TTL window
tomb.isLive();            // true for 30 s after the last note()
```

### 2.2 `shared/cloud-history-merge.cjs` — boot-hydrate local-overlay

Pure merge function. Given a cloud-view rows array (post-normalize) and
a local-rows-during-fetch snapshot, returns `{ merged, localPreserved,
localDuplicatesSkipped }`. Dedup is by `id` (the cloud's stable
`WL-<emp>-<ended_at>`) OR by `(emp_id, started_at)` composite key —
catches both the "push landed during the fetch" case and the "push
hasn't landed yet" case.

```js
const overlay = mergeCloudHistoryWithLocalOverlay(cloudRows, localRowsDuringFetch);
COMPLETED_LOGS = overlay.merged;
console.log(`[hydrate] preserved ${overlay.localPreserved} local-only row(s)`);
```

### 2.3 Wired into server.js

Three resource-level tombstones are instantiated alongside the existing
`recentFinishTombstone`. Each pull site (`refreshAbayaCatalogFromCloud`,
`refreshEmployeesFromCloud`, `refreshWorkTypesFromCloud`) gates on the
matching `isLive()`. Each local-mutation callsite calls the matching
`note()`:

| Resource | Mutation callsites (note) | Pull site (gate) |
|---|---|---|
| Catalog | `loadCatalogFromXlsxFile`, `/api/catalog` PUT, `/api/catalog-xlsx/upload` | `refreshAbayaCatalogFromCloud` |
| Employees | `loadEmployeesFromManualFile`, `loadEmployeesFromXlsxFile`, `persistEmployeeRosterAndReload` (manual-JSON branch) | `refreshEmployeesFromCloud` |
| Work types | `loadWorkTypesFromJsonFile`, `saveWorkTypesToJsonFile` | `refreshWorkTypesFromCloud` |
| COMPLETED_LOGS | n/a (one-shot boot pull) | `hydrateCompletedLogsFromCloud` uses `mergeCloudHistoryWithLocalOverlay` |

The boot log now reports all three tombstones so an operator inspecting
factory logs sees the guards are active:

```
Recent-finish tombstone: ttl=600s (defends kiosk against cloud-stale resurrection)
Catalog local-mutation tombstone: ttl=30s (defends abaya_catalog pull against LAN-fresher edits)
Employees local-mutation tombstone: ttl=30s (defends roster pull against LAN-fresher edits)
Work-types local-mutation tombstone: ttl=30s (defends work-types pull against LAN-fresher edits)
```

## 3. What changes for the factory

### 3.1 Operator-visible behavior

- **Catalog edits** — marking `is_custom = 1` on `abaya_id 3439` (or
  any other row) now sticks. The next 60 s pull is skipped (tombstone
  live for 30 s after the local edit + push). After the push lands,
  the cloud version increments and the next pull is a no-op (no
  overwrite). Operator no longer needs to re-edit after every refresh.

- **Employee CRUD** — adding, removing, renaming an employee via the
  kiosk PUT (or via direct manual JSON edits) sticks. The 60 s pull
  is skipped while the tombstone is live.

- **Work types** — adding "Stone Work" (or any new process name) via
  `/api/admin/work-types` sticks.

- **Boot hydrate** — first-morning Finish taps during the 5-30 s
  `/api/state/history` round-trip are preserved. The hydrate
  completes, the local-only rows are appended to the cloud view, and
  the operator sees a complete day's data on the dashboard.

### 3.2 Boot log

The new boot log lines tell the operator (and the verification
Playwright tests) that all four guards are active:

```
Recent-finish tombstone: ttl=600s ...
Catalog local-mutation tombstone: ttl=30s ...
Employees local-mutation tombstone: ttl=30s ...
Work-types local-mutation tombstone: ttl=30s ...
```

If a TTL is set to 0 by a misconfigured env var, the boot log shows
the floored value (5 s) instead — the operator sees that the floor
kicked in and the guard is non-zero.

### 3.3 Env vars

Optional overrides for the three resource tombstones:

```bash
# .env on the factory server (or install/.env.production)
RECENT_CATALOG_MUTATION_TOMBSTONE_MS=30000   # default 30 s; floor 5 s
RECENT_EMPLOYEES_MUTATION_TOMBSTONE_MS=30000 # default 30 s; floor 5 s
RECENT_WORK_TYPES_MUTATION_TOMBSTONE_MS=30000 # default 30 s; floor 5 s
```

If unset, the 30 s default applies. Floor is 5 s so a misconfigured
env var (e.g. `=0` or `=abc`) can't pin a tombstone at zero and
silently disable the guard.

## 4. What does NOT change

- `recentFinishTombstone` (v1.2.51) — unchanged. Still keyed by
  `emp_id`, still 10 min default, still gates `refreshCloudToday`'s
  merge per-emp.
- `mergeCloudActiveIntoLocal` — unchanged. The v1.2.51 cloud-active
  merge logic still skips live `recentFinishTombstone` entries.
- `cloudActiveMerge` audit test — unchanged. The 14 cases that pin
  the v1.2.51 merge behavior all still pass.
- `seedRosterFromCloudIfLocalMissing` — unchanged. This is the
  boot-time seed FROM cloud, not a periodic pull, so the tombstone
  guard doesn't apply.
- `loadEmployeesFromManualFile` — still only triggers on disk-file
  reload (chokidar-driven), not on every server boot. The tombstone
  note is harmless overhead in that path.

## 5. Known gaps (documented, not fixed in v1.2.52)

Three sibling paths share the same root cause but are NOT yet
defended — they're documented in AGENTS.md §11.3 "Known gaps":

1. **Multi-laptop LAN-B race** — if Laptop A's push fails AND Laptop
   B's pull runs before the next retry, Laptop B's view overwrites
   Laptop A's edit. Tombstone only defends single-laptop. 30 s TTL
   bounds worst case. Fix needs a cloud-side "row touched" cache or
   LAN coordination; both out of scope.

2. **Cloud-pulled catalog with no LAN→cloud push** — the
   `loadCatalogFromXlsxFile` auto-watch path mutates `abayaCatalog`
   locally but doesn't push to the cloud. The tombstone defends the
   LAN for 30 s; after that, the pull CAN revert the auto-reload.
   Missing-push is a separate feature/bug.

3. **Cloud-pulled roster during the LAN-side pre-hydrate window** —
   `seedRosterFromCloudIfLocalMissing` is a one-shot boot seed, not
   a periodic pull. Not relevant to the tombstone guard.

These are tracked in AGENTS.md §11.3 so the next bug in this class is
recognized immediately.

## 6. Tests

**40 new tests, all green.** Three new test files:

- `tests/recent-mutation-tombstone.test.mjs` (13 cases) — the helper:
  TTL behavior, NaN/Infinity rejection, custom clocks, clear,
  default TTL is 30 s.

- `tests/cloud-history-merge.test.mjs` (15 cases) — the merge helper:
  empty inputs, cloud-only, local-only, mixed-no-overlap, overlap by
  id, overlap by composite key, malformed-row handling, multiple
  local rows same key, custom extractors, output immutability,
  realistic mixed load (276 + 2 cloud + 4 local + 2 dups).

- `tests/server-cloud-pull-guards.test.mjs` (12 cases) — wiring audit
  via source-grep: requires the new shared modules are imported, the
  three tombstones are instantiated exactly once, every pull gate
  calls the right `isLive()`, every mutation site calls the right
  `note()`, the boot log surfaces all three tombstones, the hydrate
  uses the merge helper (no raw `COMPLETED_LOGS = hydrated` overwrite).

**Repo total: 255 tests (was 215 before v1.2.51 + v1.2.52).** Pre-existing
failures (24, all unrelated to v1.2.52):

- 17 sql.js path-resolution tests on Windows (documented in
  AGENTS.md §10; the sql.js WASM binary path differs on Windows vs
  POSIX, breaking the snapshot-writer tests on dev-box but not in
  CI). v1.2.52 doesn't touch sql.js.
- 2 LAN-side regressions documented in v1.2.50 release notes
  (`v1.2.31 req_finishWork` and `v1.2.32 dropGhostActiveSessions`).
- 2 `recent-finish-tombstone.test.mjs` cases that assert a 10-min
  default but the helper currently defaults to 5 min. Pre-existing

## 8. Apply when

If you add a new cloud→LAN pull path that mutates local state
(catalog, employees, work-types, or any future resource), add a
tombstone + `note()` callsites + tests. Don't ship the pull without
the guard. See AGENTS.md §11.3 for the pattern.

If the user reports "my edit vanished" / "this row came back from the
cloud after I changed it locally" — check AGENTS.md §11.3. The fix
is a tombstone at the pull, mirroring v1.2.52's pattern.

The verify-deploy.mjs run for v1.2.52 should include the four
"Local-mutation tombstone active" log lines in the post-deploy
verification (visible at factory boot). If a TTL shows 0 in the log,
the floor didn't kick in — bug.
