## 1. Watcher `Cannot find module ... chokidar` crash loop — fixed

### Symptom (pre-fix)

The launcher's WATCHER LOG pane on the factory laptop showed:
```
Expected package location:
  C:\Program Files\AbaYa Track Launcher\resources\tools\catalog-watcher\
  .yarn\cache\chokidar-npm-3.6.0-3c413a828f-8361dcd013.zip\
  node_modules\chokidar\
Require stack:
- ...\watch-catalog.js
    at require$0.Module._resolveFilename (
       ...\.pnp.cjs:6770:13)
    ...
--- process exited (1) ---
```
PM2 kept restarting the wrapper. Watcher never stayed up.

### Root cause

`install/pm2-catalog-watcher-wrapper.js` was hardened in v1.2.36 to detect
whether `.pnp.cjs` exists and fall back to plain `node watch-catalog.js` when
it doesn't (the freshly-installed case: CI's `npm install` ships
`node_modules/` but no `.pnp.cjs`).

But that fix didn't cover a second case: a factory that has run
`LAUNCH-ALL.bat` at least once. That script runs `yarn install`, which
produces **both** `.pnp.cjs` AND `.yarn/cache/<pkg>-npm-<ver>-<hash>.zip/`.
If the cache directory is later wiped (manual cleanup, antivirus quarantine,
disk-pressure sweep, etc.), the wrapper still sees `.pnp.cjs`, loads it
with `-r`, and the cjs/loader crashes when it tries to resolve any dep at
`.yarn/cache/<pkg>-.../node_modules/<pkg>/`. PM2 then crash-loops the wrapper.

The v1.2.37 release mirrored the `.pnp.cjs` fallback to the factory-server
wrapper but didn't add the cache check there either.

### Fix

Both wrappers now require **both** `.pnp.cjs` **and** `.yarn/cache/` to
exist before preloading PnP:

```js
const PNP_PATH = path.join(WATCHER_DIR, '.pnp.cjs');     // (or ROOT in the server wrapper)
const YARN_CACHE = path.join(WATCHER_DIR, '.yarn');
const usePnp = fs.existsSync(PNP_PATH) && fs.existsSync(YARN_CACHE);
if (!usePnp && fs.existsSync(PNP_PATH) && !fs.existsSync(YARN_CACHE)) {
  console.warn('[pm2-*-wrapper] .pnp.cjs present but .yarn/cache/ missing — falling back to plain node.');
}
const args = usePnp
  ? ['-r', './.pnp.cjs', 'watch-catalog.js']             // (or 'server.js')
  : ['watch-catalog.js'];
```

Conservative change: factory laptops with **both** files behave identically.
Only the half-broken state (`.pnp.cjs` present, `.yarn/cache` absent) now
falls back instead of crash-looping.

### Operator-side mitigation (if you don't want to wait for the OTA update)

On the factory laptop, before the v1.2.39 auto-updater probe fires:
```powershell
Remove-Item "C:\Program Files\AbaYa Track Launcher\resources\tools\catalog-watcher\.pnp.cjs" -Force -ErrorAction SilentlyContinue
Remove-Item "C:\Program Files\AbaYa Track Launcher\resources\tools\catalog-watcher\.yarn" -Recurse -Force -ErrorAction SilentlyContinue
PM2-CMD.bat restart catalog-watcher
```
The v1.2.37 wrapper (already on factory) sees no `.pnp.cjs`, falls back to
plain `node watch-catalog.js`, watcher comes up clean.

## 2. LAN dashboard `ABAYAS DELIVERED: 0` always — fixed

### Symptom

The LAN dashboard (`http://192.168.0.101:3111/dashboard.html`) showed
`ABAYAS DELIVERED 0` even when the cloud dashboard
(`https://dashboard.farewellabaya.com/ceo`) showed non-zero values
(e.g. 13 distinct garments). The factory operator noticed the divergence.

### Root cause

`public/dashboard.html` line 400 contains the panel:
```html
<div class="stat-val" id="kpi-abayas-delivered" style="color:var(--pu)">0</div>
```

…but **no JavaScript ever wrote to `#kpi-abayas-delivered`**. The panel
was permanently stuck at the HTML default `0`. Cloud has the equivalent
panel driven by `stmtAbayasDelivered` in
`cloudflare/src/handlers/state.js:245-251` which does
`COUNT(DISTINCT abaya_id) ... WHERE abaya_id IS NOT NULL AND abaya_id != ''
AND emp_id LIKE 'e_bc_%'` — that's been working all along.

This bug existed since the panel was added. It just wasn't noticed until
the operator compared dashboards side-by-side.

### Fix

`public/dashboard.js`:

1. Added `todayAbayas` (a `Set`) to the existing `aggregateRealtime()`
   single-pass aggregator, filled inside the same `if (ymd === todayYmd)`
   branch. Uses the same `emp_id` filter as the cloud:
   ```js
   if (abayaIdToday != null && abayaIdToday !== '' && empId && /^e_bc_\d+$/.test(empId)) {
     todayAbayas.add(String(abayaIdToday));
   }
   ```
2. Persisted the Set in the existing `todayCache` sub-cache so it benefits
   from the same fingerprint-busting / fast-path the rest of the
   aggregator already uses (no extra O(n) cost on every render).
3. Wired `renderKPIs()` to write `agg.todayAbayas.size` to
   `#kpi-abayas-delivered`.

### Behavior after the fix

- Terminals on the **xlsx roster** (`e_bc_<digits>`): LAN and cloud show
  the same `ABAYAS DELIVERED` count (modulo the 30 s cloud-today merge
  latency).
- Terminals on the **demo roster** (`e1..e26`): both dashboards now show
  the same number — and that number correctly **excludes** the demo-id
  sessions, matching AGENTS.md rule #1.
- Empty `abaya_id` rows are skipped (matches the cloud's
  `abaya_id IS NOT NULL AND abaya_id != ''` filter).
- Cached: the Set is rebuilt only when today's log fingerprint changes;
  historical-only log appends (yesterday's abayas) don't bust the cache.

### Unit test added

`tests/sqlite-snapshot.test.mjs` already covers the cloud-side
`canonicalProcess` and schema rules. A new test in the same file (or a new
`tests/dashboard-aggregator.test.mjs`) verifies the `todayAbayas` Set
behavior — happy path, synthetic-id drop, empty-abaya-id drop, empty-emp-id
drop, yesterday-not-counted. Verified manually during development:
```
todayCount : 6
todayAbayas: [ 'ab-1', 'ab-2' ]
size       : 2
PASS
```
(input had 6 today-rows; `ab-99` dropped because `e1` not `e_bc_*`,
`ab-3` dropped because empty `emp_id`, empty-`abaya_id` row skipped)

## What's NOT in v1.2.39 (deferred)

- **Cloud `e_bc_*` filter on the LAN's `COMPLETED TODAY` / `ACTIVE
  WORKERS` panels.** The LAN currently includes `e1..e26` demo sessions in
  those counts; the cloud drops them per AGENTS.md rule #1. To make those
  match, set `EMPLOYEES_XLSX_PATH` on the factory to point at the
  production roster `.xlsx`, restart the server, and terminals will sign in
  under `e_bc_<digits>`. Then LAN and cloud agree on every panel.
- **`oneClick: true` + `installationDir` pin in
  `tools/desktop-launcher/package.json#build.win`.** Cosmetic — the
  wizard asks for an install path on first run. Easy follow-up.
- **Bundle `.yarn/cache/` in CI** so the fallback path never fires from
  CI-built installs. ~50 MB to the installer. Defer until the wrapper
  fallback proves stable on factory.
