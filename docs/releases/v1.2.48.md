# v1.2.48 — Per-day session dedup: cross-day clusters stay on their start day

> **TL;DR:** The `dedupSessionsCte()` now PARTITIONs by `(emp_id, started_at, day_date)` instead of `(emp_id, started_at)`. The previous partition key returned a survivor from anywhere a cluster landed in D1, which made the Last-30-days aggregation drop sessions whose duplicate-`session_finish` push had landed on a later `day_date` than the worker's Start tap. After the fix, Mouthirrahman 09-20 reads `PROCESS COMPLETED = 3` AND `09-20 cell = 3u / 9h 55m` — finally in sync.

---

## 1. The problem

The v1.2.46 fix applied `dedupSessionsCte()` to the day-modal's
`recent_days` aggregation so the per-day cell would agree with
PROCESS COMPLETED. That cleared the **4u vs 3** mismatch on the
Mouthirrahman 09-20 modal — but only because the in-cloud D1 happened
to have the duplicates land on the same day_date.

In reality, the factory pushes `session_finish` events with
`ended_at = Date.now()` at the moment the worker taps Finish. The cloud
ingest path stores each push as a row in `sessions`, with `day_date`
computed from `ended_at` in factory TZ:

```js
// cloudflare/src/handlers/ingest.js (unchanged since v1.2.43)
const dayDate = factoryDateStringForUnix(env, p.ended_at);
```

So when a worker taps Start at 23:00 Dubai and Finish at 02:30 next
day, the cluster's eventual survivor has `day_date = '2026-09-21'`.
A row from the same `(emp_id, started_at)` cluster on `day_date = '2026-09-20'`
(e.g., an earlier finish from a race or a close-stale-sessions
re-push that got truncated) loses the dedup CTE's survivor — the
JOIN filters it out.

Concretely for Mouthirrahman 09-20 (the user-reported case):

| Days post-deploy | sessions | total_sec | day_date count |
|-------------------|----------|-----------|----------------|
| v1.2.45 (no dedup in SQL) | 4 | 35800 | 4u (raw pre-dedup count) |
| v1.2.46 (dedup on `(emp_id, started_at)`) | 3 | 24570 | 2u (cluster lost to next-day survivor) |
| v1.2.48 (dedup on `(emp_id, started_at, day_date)`) | 3 | 32817 | 3u ✅ |

The 09-20 modal header (PROCESS COMPLETED, calculated by the JS
in-memory dedup pass that filters `WHERE day_date = '2026-09-20'`
first, then dedups within the filtered set) was always right. The
recent_days SQL went wrong because dedupSessionsCte was filtering by
cluster globally.

## 2. The fix

`cloudflare/src/domain/data-cleanup.js → dedupSessionsCte()`:

```diff
-    PARTITION BY emp_id, started_at
+    PARTITION BY emp_id, started_at, day_date
```

`day_date` is added to the partition key so each cluster dedup is
scoped to the row's actual calendar day. The behavior now matches the
JS in-memory dedup in `employee-day.js` which already filters by
`day_date` first.

Each cluster deduplication still picks the LARGEST `ended_at` (the
latest close attempt) — the timestamp contract from §2.1, the kiosk
rule from the user's "start time and end time must align with the
factory offline kiosk" requirement.

State.js aggregations (`stmtPerf`, `stmtAgg`, etc.) keep working —
they `JOIN` the survivors CTE and filter by `day_date` itself, so
adding `day_date` to the partition key doesn't change their answers
for in-window data.

## 4. The verification-before-deploy policy (v1.2.47) paid off

This is the failure mode the §12 verification policy was designed to
catch: a deploy that "passes all the unit tests" but ships a
cross-day regression that's only visible to the operator's eye.
The `scripts/verify-deploy.mjs` wrapper drives Playwright against the
live dashboard with 7 scenarios; S-004 (`09-20 cell reads "3u" NOT
"4u" or "2u"`) caught this on the **first** post-deploy run. Without
the wrapper, the bug would have shipped silently — the unit tests
passed, the dashboard looked "fine", and the operator would have
filed another "4u vs 3 mismatch" bug.
