# v1.2.42 — One-time cleanup of two ghost active_sessions on the cloud

> **TL;DR:** Two stuck rows on the cloud D1's `active_sessions` table —
> `e_bc_999998` (Tailor (01), 17 days old) and `e_bc_00000141` / Ashanfi /
> EMP141 (Ari Work, 16 days old) — were leaking through to the Live
> Active Sessions tile on `dashboard.farewellabaya.com` even though
> neither employee exists in the current roster. Migration `0018` already
> prevents new ghosts (its `RAISE(IGNORE)` trigger blocks any future
> insert that doesn't match `e_bc_<digits>`), but it never cleaned the
> pre-existing rows. This release ships migration `0022` to drop the two
> specific ghosts. No code or schema change.

## 2. Why the live tile kept showing them

- The cloud `stmtActive` query in
  `cloudflare/src/handlers/state.js` does **not** add a
  `WHERE emp_id LIKE 'e_bc_%'` filter (deliberate — the regex would
  swallow these ids since both match it). The other aggregations
  (perf, daily, proc split, hourly) all do filter, which is why these
  two only leaked into the Live tile and never into the per-employee
  counts.
- Migration `0017_remove_synthetic_emp_sessions.sql` (2026-08-30)
  deleted stale rows from the `sessions` table only. The matching
  `active_sessions` rows were never cleaned.
- Migration `0018_reject_synthetic_emp_ids.sql` (same day) added a
  `BEFORE INSERT … RAISE(IGNORE)` trigger that **prevents new ghosts**
  but does nothing to the existing ones.

So the ghosts are pre-0018 leftovers. The cloud's `data/ceo-ingest-rejected.jsonl`
(27 MB) shows that the runtime guard has been rejecting ~5,000+ synthetic
finishes since the trigger landed, so future ghosts cannot appear.

---

## 3. The fix

New migration `cloudflare/migrations/0022_cleanup_ghost_active_sessions.sql`:

```sql
DELETE FROM active_sessions
 WHERE emp_id IN ('e_bc_999998', 'e_bc_00000141')
   AND (emp_name IS NULL OR emp_name = '')
   AND (emp_code IS NULL OR emp_code = '');
```

Three guards on the WHERE clause so a future legitimate roster change
cannot accidentally re-target these ids:

1. The id is exactly one of the two known ghosts.
2. `emp_name` is null/empty.
3. `emp_code` is null/empty.

If a real employee with id `e_bc_00000141` joins the roster later (with
a real name and code), the predicate fails to match, the DELETE is a
no-op for that row, and the operator can investigate manually.

Re-running step 2 after a successful first run reports
`meta.changes = 0`. Safe.

### 3.3 Rollback

`active_sessions` is the runtime live state, not historical data. If
somehow one of these rows is needed back (it shouldn't be — both have
been idle 16+ days and the factory server never received a matching
finish), the operator can re-INSERT from a saved snapshot, but at this
point the practical move is to ask the factory worker to tap Start
again on their station.

## 4. Why the offline `.db` is untouched

The user explicitly chose **"Cloud D1 active_sessions only"**. The
local snapshot's `active_sessions` table is populated from the cloud
`/api/state` response on every snapshot write
(`shared/sqlite-snapshot.cjs → insertActive`). Once the cloud is clean,
the next local snapshot (~5 min later, when the factory server's
`sqlite-snapshot.cjs` writer runs) will not see these rows in the
incoming `activeSessions` object and the local copy will sync down
automatically.

We did **not** touch `sessions.emp_id IN ('e_bc_999998', ...)` in the
offline `.db`. Those 2 finished `sessions` rows are 16+ days old, not on
the live tile, and the factory server is the source of truth for
`sessions` (per AGENTS.md §1 + the timestamp contract §2). The cloud
already deleted them via migration `0017`. If the operator wants the
offline copy in lock-step, a separate pass is needed — not in scope
here.

## 7. Future-proofing (deferred)

- **State handler should filter `LIKE 'e_bc_%'`** on `stmtActive` too,
  even though the regex catches both ghosts. A future scenario where
  someone pushes `e_bc_7777` (a real barcode nobody uses yet) with a
  valid name would still leak through if the worker never finishes.
  Filed as a candidate for v1.2.43.
- **Migration `0017` should be extended to `active_sessions`** at
  some point, but doing it now would re-run on every fresh install and
  blank any in-flight session if the operator ever rolled back. Safe
  only as a one-shot, so leaving 0022 manual is correct.
