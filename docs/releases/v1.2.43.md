# v1.2.43 — Fix duplicate session rows + canonicalize 5 missing work types

> **TL;DR:** The cloud dashboard's per-employee daily report was showing
> 3-8 rows for the same session (same started_at, different ended_at).
> This was the factory's `close-stale-sessions` endpoint pushing a fresh
> `session_finish` each time it was called on the same orphan — the
> cloud D1 `sessions` PK is `WL-<emp_id>-<ended_at>` so every variant
> was a new row. Three layers of fix in this release: (1) cloud migration
> `0023` deletes the historical duplicates, (2) `server.js` adds an
> idempotency check that suppresses re-pushes, (3) `employee-day.js`
> dedups at read time as defense in depth. Plus the 5 work-type names
> that were silently passing through unchanged (`Complete`,
> `Incomplete`, `Show Button`, `Alter`, `Cutting`) now canonicalize
> properly and bucket into `daily_stats`.

---

## 1. The bug

Screenshot from `dashboard.farewellabaya.com` (2026-09-17 ~23:37 Dubai):

```
Wahid — 2026-09-16
Packaging · Generated: 9/17/2026, 11:37:47 PM
PROCESS COMPLETED 3
WORK TIME          28h 47m 18s
LIVE NOW           0s
LAST 30 DAYS (12 days with 1u, 1u, 1u, 1u, 1u, 1u, 6u, 1u, 2u, 2u, 2u, 2u,
                3u, 2u — 09-16 is the 3u outlier)

SESSIONS:
  TIME                PROCESS        ITEM           DURATION
  8:55 PM – 11:04 AM  Tailor (01)    CF111 STD-O    4h 39m 17s
  8:55 PM – 7:03 PM   Tailor (01)    CF111 STD-O    11h 8m 46s
  8:55 PM – 9:54 PM   Tailor (01)    CF111 STD-O    12h 59m 15s
```

Three rows for one session — same started_at (8:55 PM), same process,
same abaya, but three different end times. The operator's natural read
was "Wahid did three sessions", when in reality Wahid tapped Start once
and the orphan was closed three times.

### 1.1 Root cause

Two paths on the factory LAN push `session_finish` to the cloud:

- **`req_finishWork` socket handler** — worker taps Finish. Idempotent
  by construction: the worker taps Finish once per Start.
- **`/api/admin/close-stale-sessions` admin endpoint** — operator
  script (`scripts/reset-orphan-sessions.ps1`) closes stuck orphans
  with a synthetic end time = `min(started + 8h, now)`. **Not**
  idempotent: every time the script is called on the same orphan, it
  pushes a fresh `session_finish` with `auto_closed: true`.

The factory's offline-report persistence uses
`setImmediate(persistOfflineDashboardReport)` after a close. If the
LAN server is restarted (power blip, deploy, manual restart) before
the setImmediate fires, the offline-report's `active` block still
contains the orphan. Next boot re-hydrates ACTIVE_SESSIONS, the
operator (or a cron) runs close-stale again, and a duplicate
`session_finish` is pushed.

The cloud D1's `sessions` table has PK = `'WL-' + emp_id + '-' + ended_at`,
so each push lands as a new row.

### 1.2 The data

Offline snapshot at `data/sqlite-snapshots/abaya-snapshot-latest.db`
mirrors the cloud state. As of 2026-09-17 18:16 UTC:

```
28 (emp_id, started_at) clusters have duplicates
79 total rows in those clusters
51 extra rows that should not exist
Largest cluster: e_bc_00000138 (Wahid) — 8 rows sharing started_at=1788156388
                 (2026-08-31 06:06:28Z, ended_at spread Aug 31 → Sep 9)
```

The cloud dashboard has accumulated these over multiple factory-server
restarts since late August. The duplicates inflate Wahid's PROCESS
COMPLETED count (1 real session → 8 cloud rows), blow up WORK TIME
(the 8 rows have `duration_sec` values 79200 (= 22h) and 86400 (= 24h)
so SUM = ~170h for a single 7-day abaya run), and break the LAST 30
DAYS heatmap (Wahid's day cells show inflated unit counts).

## 2. The fix

### 2.1 Cloud migration `0023` — historical cleanup

`cloudflare/migrations/0023_dedup_sessions_per_emp_started_at.sql`:

```sql
CREATE TEMP TABLE _session_dedup_winner AS
SELECT id FROM (
  SELECT id, ROW_NUMBER() OVER (
           PARTITION BY emp_id, started_at
           ORDER BY ended_at DESC, id DESC
         ) AS rn
    FROM sessions
) WHERE rn = 1;

CREATE TEMP TABLE _session_dedup_loser AS
SELECT s.id FROM sessions s
  LEFT JOIN _session_dedup_winner w ON w.id = s.id
 WHERE w.id IS NULL;

DELETE FROM sessions WHERE id IN (SELECT id FROM _session_dedup_loser);
```

Keep the row with the **largest `ended_at`** per `(emp_id, started_at)`
cluster. That's the latest close attempt and reflects the actual end
of work. Earlier closes were either (a) superseded by a real worker
Finish later that day, or (b) redundant orphan-close pushes.

**Verified locally** on the offline snapshot replica: 28 clusters → 0
clusters after the DELETE, 314 → 263 rows (51 deleted, matches the
audit exactly). ROW_NUMBER() OVER (...) is supported on Cloudflare D1
as of `compatibility_date: 2024-11-01` (set in `cloudflare/wrangler.toml`).

#### Run sequence (operator)

```powershell
cd "C:\Users\mabba\Desktop\AbaYa-Track-v1.0.2\cloudflare"

# 1. Dry-run — preview what would be deleted.
npx wrangler d1 execute abaya-db --remote --command="
  SELECT emp_id, started_at, COUNT(*) AS dup_count,
         MIN(ended_at) AS first_end, MAX(ended_at) AS last_end
    FROM sessions
   GROUP BY emp_id, started_at
  HAVING COUNT(*) > 1
   ORDER BY dup_count DESC LIMIT 50;
"
# Expect ~28 clusters, ~51 extra rows.

# 2. Apply.
npx wrangler d1 execute abaya-db --remote \
  --file=migrations/0023_dedup_sessions_per_emp_started_at.sql

# 3. Verify — must show 0.
npx wrangler d1 execute abaya-db --remote --command="
  SELECT COUNT(*) AS dup_groups_remaining
    FROM (SELECT 1 FROM sessions
           GROUP BY emp_id, started_at HAVING COUNT(*) > 1);
"
```

**Idempotent**: re-running the migration after a successful first run
matches 0 rows. **No rollback path** — once deleted from D1 the
duplicates are not recoverable. Take a `wrangler d1 export` first if
you want a safety net.

### 2.2 Server-side idempotency — prevents new duplicates

Two new helpers in `shared/session-dedup.cjs`:

```js
function isDuplicateSessionFinish(completedLogs, emp_id, started_at_ms) {
  // O(N) scan; COMPLETED_LOGS is bounded by OFFLINE_LOG_WINDOW_MS (~7 days).
  // Returns true if a row with the same (emp_id, start) exists.
}
```

Wired into both close paths in `server.js`:

- **`req_finishWork`** — before `pushToCloudflare('session_finish', ...)`,
  if `isDuplicateSessionFinish(COMPLETED_LOGS, emp_id, record.start)`,
  skip the push with a `[req_finishWork] skipping duplicate cloud push`
  log line. Defensive only — the worker shouldn't be able to tap
  Finish twice on the same Start.
- **`/api/admin/close-stale-sessions`** — same check, but **also**
  drops the in-memory `ACTIVE_SESSIONS[emp_id]` row so the next call
  sees an empty actives list (already-closed). The endpoint returns
  `alreadyClosed: true` in the per-emp results so the operator's
  PowerShell script knows what happened.

The helper handles both legacy `start` (ms) and new `started_at` (ms)
field names per AGENTS.md §2 (timestamp contract). Eight unit tests in
`tests/session-dedup.test.mjs` exercise the empty/null/missing inputs,
same/different emp_id, same/different start, both field-name shapes,
string-typed values, and a replica of the actual Wahid dup cluster
shape from the operator's report.

### 2.3 Read-time dedup in `employee-day.js`

`cloudflare/src/handlers/employee-day.js` — after the D1 query
returns, group the sessions array by `started_at` and keep the row
with the largest `ended_at`. This is defense in depth: even if a
future bug pushes a duplicate, the dashboard won't show it.

The `totals.units` field is now derived from the deduplicated
sessions (not raw `rows.length`), so the per-day "PROCESS COMPLETED"
count matches what the operator sees in the sessions list.

A regression test in `tests/ceo-report.test.mjs` (`handleEmployeeDay
dedups duplicate (emp_id, started_at) clusters`) reproduces the
exact Wahid 8/31 cluster shape and asserts that the response has
1 winner + 1 distinct = 2 sessions (not 4 raw rows).

### 2.4 Work-type canonicalization — coverage for 5 missing names

`cloudflare/src/domain/process.js` and its mirror in
`shared/sqlite-snapshot.cjs` add:

| Input (any case) | Canonical | Daily column |
|---|---|---|
| `Cutting`, `cutting` | `Cutting` | `tailor_01_units` |
| `Show Button`, `show button` | `Show Button` | `button_units` |
| `Alter`, `alter` | `Alter` | `tailor_01_units` |
| `Complete`, `complete` | `Complete` | `tailor_01_units` |
| `Incomplete`, `incomplete` | `Incomplete` | `hand_work_units` |

These names were in `data/work-types.json` but missing from the
cloud's `WORK_TYPES` constant in `process.js` and the local mirror.
Sessions carrying these names were passing through unchanged and
landing in the daily_stats rollup with their literal string as the
process column — visible on the per-process split chart but **not**
counted in any `*_units` column.

After this release, they bucket into existing columns (no schema
change needed). The `SUMMARY_WT_CASES` SQL in `process.js` is
extended so `tailor_01`, `hand_work`, and `button` aggregates
include the new aliases:

- `tailor_01` ← `Tailor (01)`, `Cutting`, `Cutting master`, `Alter`, `Complete`
- `hand_work` ← `Hand Work`, `Finishing`, `Incomplete`
- `button` ← `Button`, `Show Button`

Six new cases added to the alias matrix test in
`tests/sqlite-snapshot.test.mjs`.

#### Mapping rationale (per the operator's domain knowledge)

The user-visible bucket (which `*_units` column the data lands in)
follows these conventions:

- `Complete` and `Alter` are last-station / alteration work that
  routes through Tailor 1's stitching, so they count toward
  `tailor_01_units`.
- `Incomplete` is the backflow marker when a worker taps Start but
  the station isn't ready; the most common next-station is Hand
  Work, so it buckets there.
- `Show Button` is a sub-station of Button; same column.
- `Cutting` was already mapped to `tailor_01_units` historically;
  preserved for backward-compatibility with existing daily_stats
  rows. The unused `cutting_units` column is not written to.

If any of these mappings are wrong for the floor's actual workflow,
update `PROCESS_TO_DAILY_COL` in both `process.js` and
`sqlite-snapshot.cjs` in the same commit; the test in
`tests/sqlite-snapshot.test.mjs` will catch drift at CI.

## 7. Post-release incident: 0023 disaster + D1 Time Travel recovery (2026-09-19)

When the operator first tried to apply this migration in production,
the `CREATE TEMP TABLE` form used in the migration body caused the
`wrangler d1 execute --file` import path to time out twice (the
upload step completed but the processing step never returned a result
through the wrapper). A subsequent hand-rewrite that pushed the SQL
inline as `--command "DELETE ... WHERE id IN (SELECT ... WHERE rn > 1)"`
parsed the semicolon-separated statement in a way that **dropped the
ROW_NUMBER() filter**, matching every row in `sessions` rather than
just the dup losers. Wrangler reported `changes: 7680, rows_written:
7680` — accurate.

The result: **~7,600 historical `sessions` rows were deleted** from
the cloud, leaving only the most recent ~74 rows (last 3 days of
activity).

### Recovery (worked)

D1's **Time Travel** feature kept a bookmark from the moment right
after the 0022 ghost cleanup had landed (and before 0023 was
attempted). Restoring to that bookmark:

```powershell
cd cloudflare
npx wrangler d1 time-travel restore abaya-db `
  --bookmark=000008af-00000174-000050eb-8901df9483641d8874941a429f33b32a
# Output: "Database abaya-db restored back to bookmark ..."
# Output: "To undo this operation, you can restore to the previous bookmark: <next-bookmark>"
```

Brought `sessions` back to 7,680 rows and `daily_stats` back to its
pre-disaster 142 rows. The 0022 ghost cleanup was preserved (ghosts
already gone), the bad DELETE was undone.

After restore, 0023 was re-applied using the **safe CTE form** below
(this is now the canonical form in `migrations/0023_*.sql`).

### The safe CTE form (save yourself the same mistake)

The original migration used two `CREATE TEMP TABLE`s because I worried
about D1 not supporting window functions in subqueries. That worry
was unfounded. D1 SQLite (compatibility_date 2024-11-01) supports
window functions inside CTEs fine, and the CTE form is a single
statement that does not depend on `--file` mode surviving a multi-
statement upload session.

```sql
WITH ranked AS (
  SELECT id, ROW_NUMBER() OVER (
           PARTITION BY emp_id, started_at
           ORDER BY ended_at DESC, id DESC
         ) AS rn
    FROM sessions
)
DELETE FROM sessions
 WHERE id IN (SELECT id FROM ranked WHERE rn > 1);
```

This form:
- **Ships as a single statement**, so `wrangler d1 execute --command`
  parses it cleanly (no `;` ambiguity, no temp tables to lose between
  statements).
- **Returns `changes: 355` exactly** for the original 179-cluster
  scenario — verified twice on the same D1.
- **Idempotent**: re-running matches 0 rows.

### Lesson (operator + future agents)

1. **Always run `--command` with a SELECT-only dry-run first** when
   the migration involves a DELETE, even if a `--file` migration
   exists. The CTE makes the dry-run trivial:
   ```sql
   WITH ranked AS (...ROW_NUMBER...)
   SELECT COUNT(*) AS would_delete FROM ranked WHERE rn > 1;
   ```
2. **Wrangler's `changes: N` for a DELETE is the number of rows
   actually deleted**, not the number of rows that matched the
   predicate. If you read a `changes: 7680` when you expected 355,
   something went wrong — abort, do NOT trust the result.
3. **D1 Time Travel is the rollback path**. The wrangler output of
   every run includes a "To undo this operation, you can restore to
   the previous bookmark" line — copy it before you start the next
   step. The bookmark survives across restores, so you can always
   step back further.
4. **The factory's local sqlite-snapshot has been empty (zero tables)
   for weeks** — see the v1.2.30 PM2 break entry in agent memory.
   Do NOT rely on `data/sqlite-snapshots/abaya-snapshot-latest.db`
   for restoration. The cloud's D1 Time Travel is the only
   recoverable source.
