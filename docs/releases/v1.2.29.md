# v1.2.29 — Fix: new employee does not show on kiosk (xlsx roster reload lock-order bug)

**Ship date:** 2026-09-07
**Type:** Bug fix (server.js only — no schema, no new endpoints, no .exe feature change)
**Severity:** High (operator-facing — new employees invisible on kiosk until browser refresh)

## TL;DR

Adding a new employee via `POST /api/employees` (the supervisor dashboard's
"Add employee" button, or any ingest path that calls it) used to silently
fail to update the in-memory `EMPLOYEES` array. The on-disk xlsx was
correct, but the kiosk kept showing the old roster, and the LAN dashboard
didn't get a `socket.io employees_update` event. The new employee's first
`Start` / `Finish` session also silently failed to reach the cloud because
`server.js:2240` does `if (emp) { pushToCloudflare(...) }` against the
(now stale) `EMPLOYEES` lookup. Eventual recovery: the chokidar watcher
would fire 1.5–2.5 s later and re-read the file. Until then, the operator
saw a broken kiosk.

## Root cause

In `persistEmployeeRosterAndReload` (`server.js:3204`), the **xlsx-master
branch** (line 3211) was wrapping the in-function `loadEmployeesFromXlsxFile()`
call inside the `try/finally` block that holds the `employeesXlsxWriteInProgress`
lock:

```js
// before
if (EMPLOYEES_XLSX_PATH) {
  employeesXlsxWriteInProgress = true;
  try {
    /* ... build + write xlsx ... */
    loadEmployeesFromXlsxFile();   // <-- inside the lock window
  } finally {
    employeesXlsxWriteInProgress = false;
  }
}
```

`loadEmployeesFromXlsxFile()` (line 3058) has an early-return guard at
line 3060 that says "if a write is in progress, skip". Because the call
ran while the flag was `true`, it returned without updating `EMPLOYEES`,
without rebuilding `EMP_PERF`, without calling `rebuildACMap()`, and
without firing `emitEmployeesChanged()`.

The **manual-JSON branch** (line 3228) was unaffected — it doesn't
go through xlsx reload, it sets `EMPLOYEES = nextEmployees` directly
and calls `emitEmployeesChanged()` synchronously.

## Fix

Move the `loadEmployeesFromXlsxFile()` call to AFTER the `try/finally`,
so the lock is cleared before the in-memory reload runs:

```js
// after
if (EMPLOYEES_XLSX_PATH) {
  employeesXlsxWriteInProgress = true;
  try {
    /* ... build + write xlsx ... */
  } finally {
    employeesXlsxWriteInProgress = false;   // lock released first
  }
  loadEmployeesFromXlsxFile();              // then reload — sees new mtime
}
```

`lastEmployeesXlsxMtime = 0` is set inside the try block so the function's
own mtime short-circuit at line 3073 doesn't skip the reload either.

The result: `EMPLOYEES` is updated synchronously, `EMP_PERF` is rebuilt,
`rebuildACMap()` runs, and `emitEmployeesChanged()` fires the
`io.emit('employees_update', ...)` event. Kiosks re-fetch the new roster
in < 100 ms instead of waiting 1.5–2.5 s for the chokidar recovery.

## Tests

`npm test` runs 121 / 121 green. The 3 new tests in
`tests/employees-update-propagation.test.mjs`:

1. `xlsx branch: POST /api/employees updates in-memory EMPLOYEES and persists`
   — happy path. Verified the test **fails on the pre-fix code** at
   `postBody.employee.id` (because `EMPLOYEES.find()` couldn't locate the
   just-added row), and passes on the post-fix code.
2. `xlsx branch: duplicate barcode POST returns 409 (no EMPLOYEES update)`
   — guard against the manual branch's duplicate-check regression.
3. `xlsx branch: missing required field returns 400 (no EMPLOYEES update)`
   — guard against the manual branch's required-field check regression.

The tests spawn `server.js` as a child process with a temp `ABAYA_DATA_DIR`
and `EMPLOYEES_XLSX_PATH` (so the test never touches the factory's real
data), wait for `/api/health`, then exercise the API. They use Node 18+
built-ins (`fetch`, `node:test`, `node:net`, `node:fs`) — no extra
dev-dep additions.

## What the operator sees

- **Add employee** on the supervisor dashboard → new employee appears on
  the kiosk in < 100 ms (was: 1.5–2.5 s, sometimes never).
- **New employee's first Start/Finish** now reaches the cloud correctly
  (was: silently dropped because `if (emp) { pushToCloudflare(...) }`
  failed the lookup against stale `EMPLOYEES`).
- **No data migration required.** Existing employees.xlsx is read on the
  next chokidar reload, same as before.

## What I did NOT fix (separately tracked)

- **Boot-time xlsx load**: `chokidar.watch(emp, { ignoreInitial: true })`
  at `server.js:4246` means a server restart with `EMPLOYEES_XLSX_PATH`
  set leaves `EMPLOYEES = DEFAULT_EMPLOYEES` (the 26-row demo list) until
  the chokidar sees a file change. The factory relies on cloud roster
  sync (`refreshEmployeesFromCloud()` at line 4376) to repopulate at boot,
  which masks the issue when CF is reachable but creates a brief window
  of "demo data on the kiosk" when offline. Tracked as a separate fix.

## What I did NOT change

- `HEAL_KEYS` in `env-migrate.cjs` — unchanged. Factory's `.env`
  keeps `PORT=3111`, `HOST`, `CF_WORKER_URL` after this update, same
  as v1.2.18+.
- Cloud D1 schema — unchanged. No migration needed.
- Public HTTP API — unchanged. `POST /api/employees` returns the same
  `{ok: true, employee: ...}` shape.
- Socket.io event contract — unchanged. `io.emit('employees_update', ...)`
  fires as before; the bug was that it WASN'T firing on the xlsx branch.
