# v1.2.46 — Day-modal history strip honors (emp_id, started_at) dedup

> **TL;DR:** The previous-day history strip and the empty-day "nearby dates" hint on the per-employee day modal now go through the same `dedupSessionsCte()` CTE that the rest of the cloud read path already uses. A worker-day that PROCESS COMPLETED correctly says is 3 now also reads 3 on the Last 30 Days cell — no more "4u vs 3" mismatch in front of the operator.

---

## 1. The problem

The factory CEO dashboard's per-employee day modal (`/api/report/employee-day`)
shows two numbers for the same employee on the same picked date:

- **PROCESS COMPLETED** in the stat header — driven by `data.totals.units`,
  which counts the in-modal `sessions` list after the v1.2.43 in-memory
  `(emp_id, started_at)` dedup pass.
- **The 09-20 cell** on the "Last 30 days" history strip — driven by
  `data.recent_days`, which used a separate raw SQL
  `SELECT day_date, COUNT(*) FROM sessions GROUP BY day_date`.
- **The "X units" chip** on the empty-day "nearby dates" hint — also a raw
  `COUNT(*) GROUP BY day_date`.

Until v1.2.45 the cloud had a one-time migration (0023) that cleaned the
**historical** duplicate `(emp_id, started_at)` rows. But the factory's
LAN server has no idempotency guard until v1.2.43+ deploys to every laptop,
so the moment the operator looked away, new dup clusters started piling up
again. v1.2.45 added a SQL-layer scrub on the `/api/state` aggregations
so the dashboard KPIs stayed clean — but `employee-day.js` kept its raw
`COUNT(*)` for `recent_days` and `nearby_dates`.

The result, on the Mouthirrahman day modal opened on 2026-09-23:

| Place that displays the count | Number shown |
|---|---|
| PROCESS COMPLETED (post-dedup `totals.units`) | **3** ✅ |
| Last 30 Days cell for 09-20 (raw `COUNT(*)`)   | **4** ❌ |
| Empty-day chip for 09-20 (raw `COUNT(*)`)      | **4** ❌ |

The two halves of the same modal contradicted each other. Operator-visible.

## 2. The fix

Apply `dedupSessionsCte()` (the same CTE `state.js` uses for `stmtAgg`,
`stmtPerf`, `stmtGarment`, `stmtProcSplit`, `stmtHourly`,
`stmtAbayasDelivered`) to both queries in `employee-day.js`:

- The **30-day history strip** (`recent_days`) — `SELECT s.day_date,
  COUNT(*) AS n, COALESCE(SUM(s.duration_sec), 0) AS total_sec FROM
  sessions s JOIN survivors w ON w.id = s.id WHERE ... GROUP BY s.day_date
  ORDER BY s.day_date DESC LIMIT 30`.
- The **empty-day nearby-dates hint** (`nearby_dates`) — same shape, ordered
  by `ABS(julianday(...))`.

The survivor rule is unchanged: largest `ended_at` per `(emp_id,
started_at)` cluster, with `id DESC` as the tie-break. The
`dedupSessionsCte()` definition in `data-cleanup.js` keeps being the
single source of truth (the AGENTS.md §11 contract).

## 3. Files changed

- `cloudflare/src/handlers/employee-day.js` — import `dedupSessionsCte`
  from `../domain/data-cleanup.js`; wrap both `recent_days` and
  `nearby_dates` queries with the CTE.
- `tests/ceo-report.test.mjs` — two new tests pinning the contract:
  - `handleEmployeeDay recent_days strips dup (emp_id, started_at) rows
    (v1.2.46)` — fixture has 4 raw rows on one day that should collapse
    to 2 distinct sessions.
  - `handleEmployeeDay nearby_dates strips dup (emp_id, started_at) rows
    (v1.2.46)` — fixture with a dup cluster on a different day;
    exercises the `nearby_dates` branch by returning 0 rows from the
    in-modal SELECT.
- `package.json` — version bumped to `1.2.46`.
- `tools/desktop-launcher/package.json` — version bumped to `1.2.46`.
- `AGENTS.md` — §11 amended to call out `employee-day.js`'s `recent_days`
  and `nearby_dates` as additional surfaces that must apply
  `dedupSessionsCte()`.

## 4. Tests

`npm test` now runs **176 passing**, **2 failing** (`# fail 2`). The two
failures are pre-existing v1.2.31 / v1.2.32 LAN-side regressions
unrelated to this change — they were also failing on `v1.2.45` baseline
before any of my edits (`git stash` round-trip verified).

The two new tests assert:

1. The SQL for `recent_days` and `nearby_dates` includes
   `WITH survivors AS (` and `JOIN survivors w ON w.id = s.id` (so a
   future agent can't quietly drop the CTE without breaking the test).
2. The post-dedup counts in `body.recent_days` and `body.nearby_dates`
   agree with the in-modal `totals.units` count from the v1.2.43 dedup
   pass. Fixture rows have 4 raw on one date; the test asserts the cell
   reads `2` (3 dups collapse to 1 + 1 distinct).

## 5. What factory PCs will see

Nothing visible on the dashboard until a pre-v1.2.43 LAN server pushes
new dup clusters. After this fix, the **first time** a worker-day gets a
re-pushed dup, the history strip cell and PROCESS COMPLETED will agree.
Before this fix they would disagree by however many dups that
worker-day accumulated.

## 6. Caveat — STILL applies after this fix

The dashboard's top-row "−0s" freshness pills (e.g. `0s, 0s, -9999s,
0s, 0s` under the five tiles) are still cosmetic-broken: `state.js`
sets `fetched_at_sec = serverNowTs = Date.now()`, so the browser-side
`serverNowMs - fetchedAtMs` is always 0 between polls. That's a separate
issue and not addressed in this release — pin it for v1.2.47 if it
matters to the operator.
