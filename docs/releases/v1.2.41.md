# v1.2.41 — Permanent updater bootstrap + per-metric delay labels

> **TL;DR:** Two factory-blockers are killed here, plus the realtime lane
> in v1.2.40 is extended so every KPI tile shows exactly how stale it
> is — the operator never has to guess whether "Active Workers 16" is
> from right now or from 30 seconds ago.
>
> 1. **Permanent autoupdater fix.** Factory laptops stuck on a release
>    that predates v1.2.37's `verifyUpdateCodeSignature: false` (most
>    commonly v1.2.33 in the field) can now self-recover via a one-shot
>    bootstrap. The in-app launcher gets a "Force install from cloud"
>    button; the docs also ship a `REPAIR-UPDATER-BOOTSTRAP.ps1` that
>    bypasses electron-updater entirely by downloading the EXE directly,
>    verifying SHA-512 against the manifest, and running the NSIS
>    installer silent. Once the laptop lands on v1.2.41 the in-app
>    autoupdater takes over for good.
> 2. **Per-tile freshness labels.** Every KPI tile carries a small
>    "live / −Xs / −Xm / stale" badge so the operator knows whether each
>    number reflects a sub-second SSE push, a 1 s poll, or worse. SSE
>    patches keep the cheap KPIs (active, completed, process split, hourly)
>    instant; the more expensive aggregations (avg, eff, abayas
>    delivered, garment totals) catch up within ~100 ms of every
>    factory-floor event instead of waiting the full 1 s poll cycle.

## 1. Autoupdater permanent fix

### 1.1 Symptom (recap from operator's screenshots)

Factory laptops stuck on v1.2.33 (or any release before v1.2.37) show:

```
Feed: cloud | probe: ok | Channel: stable | Current: 1.2.33 | Available: 1.2.38
LAST ERROR: 9/15/2026, 9:27:29 PM - New version 1.2.38 is not signed by
the application owner: publisherName: AbaYa Track Self Signed ...
```

electron-updater reads the publisherName of the new EXE and refuses to
install anything that doesn't match its expected publisher. From v1.2.37
onward `build.win.verifyUpdateCodeSignature: false` relaxes the check,
but a laptop stuck on a pre-v1.2.37 release can't see that change
because **the very check blocking future updates is what the new release
disables**. Classic chicken-and-egg.

### 1.2 Two paths to escape

**Path A — in-app (preferred)**: the launcher UI now ships with a
`Force install from cloud` button. It triggers an IPC handler in
`tools/desktop-launcher/main.js` that shells out to the bundled
`install/REPAIR-UPDATER-BOOTSTRAP.ps1`. No operator command-line needed;
the launcher window itself drives the recovery. When the user clicks
the button, the launcher shows progress ("force-bootstrap active"),
downloads the EXE, verifies SHA-512, runs NSIS silently, and restarts
into the new version.

**Path B — manual PowerShell**: copy
`install/REPAIR-UPDATER-BOOTSTRAP.ps1` to the factory PC and run it as
Administrator. The script:

- Reads `latest.yml` from `https://dashboard.farewellabaya.com/updates/stable/latest.yml`
  (overridable via `$env:ABAYA_CLOUD_UPDATE_BASE_URL` for LAN-mirror setups)
- Parses out the EXE URL + size + sha512 from the manifest
- Downloads the EXE
- Verifies size matches and SHA-512 matches (when present in the manifest)
- Closes any running launcher process
- Runs the NSIS installer with `/S`
- Polls the post-install `package.json` to confirm the version advanced
- Exits with a documented code (`0..7`)

The script is idempotent: running it when already on target version
returns `0` without downloading anything.

### 1.3 What the bootstrap doesn't touch

- `verifyUpdateCodeSignature: false` is still in
  `tools/desktop-launcher/package.json#build.win`. After bootstrap, the
  factory is on v1.2.41 (or whatever the script targeted) and the
  bundled `package.json` already has the relaxed check. From this
  point forward, in-app auto-updates handle everything.
- NSIS SmartScreen ("Unknown publisher") is unchanged — it's a Windows
  prompt, not an electron-updater check. The bootstrap script triggers
  the same NSIS flow the autoupdater would, so the user already
  accepted the publisher on this laptop.
- `%APPDATA%\AbaYa Track\.env` is untouched (the new install updates
  binaries, not user data). `PORT=3111` HEAL_KEYS still applies.

## 2. Per-metric freshness labels

### 2.1 What the operator sees now

Every KPI tile renders a small pill in the corner:

| Tile | State | Pill |
|---|---|---|
| Active Workers | SSE pushed < 2 s ago | `live` (green) |
| Active Workers | SSE pushed 2–10 s ago | `-Xs` (amber) |
| Completed Today | SSE patched within 2 s | `live` (green) |
| Abayas Delivered | Polled from /api/state 1–4 s ago | `-Xs` (amber) |
| Abayas Delivered | Polled ≥ 60 s ago | `-Xm` (amber) |
| Avg Session Time | Polled 100 ms ago (post-SSE refresh) | `-Xs` (faint green) |
| Avg Session Time | Polled 30 s ago | `-30s` (amber) |
| Efficiency Score | > 5 min stale | `stale` (red) |
| (no /api/state yet) | first paint | `…` (grey) |

SSE-driven tiles (active, completed) flip to "live" within ~300 ms of
every factory-floor event. Polled tiles get `-Xs` of actual seconds since
the last `/api/state` response.

### 2.2 How SSE patches catch derived KPIs up faster

Previously, ANY new event waited up to 1 s for the next `/api/state`
poll before the dashboard's reported metrics reflected it. v1.2.41
fires an immediate `?live=1` poll within 250 ms of each SSE event
(debounced — bursts collapse to a single fetch). So the dashboard's
"ABAYAS DELIVERED" goes up within ~100 ms of the new garment crossing
the last station, not 1 s later.

The freshness pill on polled tiles reflects this — a derived KPI that
just refreshed from the post-SSE poll will read `-Xs` with `X`
typically ≤ 1, in green (the `fresh ok` state). When the operator
sees `-5s` or worse on a polled tile, that's a real signal that
either events are coming in too fast for the post-SSE refresh to
keep up, or D1 itself is slow.

### 2.3 Implementation summary

- `cloudflare/src/handlers/state.js`: every `/api/state` response now
  carries `state_meta.fetched_at_sec` and `state_meta.server_now_ms`
  so the dashboard can compute per-tile age without inventing
  timestamps. Both are server-clock so the operator doesn't need to
  trust the browser's clock for this signal.
- `cloudflare/src/ui/ceo-pages.js`: each KPI tile has a new
  `<div class="kpi-fresh" data-kpi-fresh="X" data-kpi-source="sse|polled">`
  slot. `refreshKpiFreshnessLabels()` recomputes the text every 1 s.
  Called from `renderKPIs()` and at the end of every SSE `message`.
- `cloudflare/src/ui/ceo-static.js`: CSS for the four pill states
  (`fresh live`, `fresh warm`, `fresh stale`, `fresh ok`).
- SSE consumer: after every `message`, `schedulePostEventRefresh()`
  debounces 250 ms then triggers `poll(true)` so derived metrics
  catch up.

### 2.4 What stays poll-bound (and why)

These still update only on `/api/state`:

- `avg_cycle_sec_today` / `median_session_sec_today` — recompute a
  median over today's sessions; doing it per-event is too expensive
  for free-tier D1 row_reads.
- `efficiency_today` — same as above (median-based formula).
- `garment_totals_today` — needs every session today per garment.
- `employee_perf` — running aggregates per employee.

The freshness pill turns these from "we don't know if it's current"
into "we know exactly how stale this number is, in seconds." That's
the operator's actual question.

## 3. End-to-end behavior

### Scenario: factory stuck on v1.2.33 (operator screenshots)

1. Factory PC has v1.2.33 installed.
2. Operator opens launcher → Control Center → `Force install from
   cloud`. (Or runs the bootstrap script as Administrator.)
3. Bootstrap downloads `latest.yml`, parses version `1.2.41`, downloads
   `AbaYa-Track-Launcher-Setup-1.2.41.exe`, verifies SHA-512, closes the
   launcher, runs NSIS `/S`, polls post-install `package.json`.
4. Launcher restarts into v1.2.41.
5. Future updates through `Check Updates` work because v1.2.41's
   bundled `package.json` has `verifyUpdateCodeSignature: false`.

### Scenario: operator compares LAN and cloud dashboards

1. Worker taps Start on terminal.
2. LAN dashboard shows the new row via Socket.IO in < 100 ms (LAN
   has always been realtime; was already this fast).
3. Cloud dashboard:
   - `STATE.active[e_bc_…]` is updated by SSE in < 300 ms.
   - `STATE.completed_today` flips via SSE for Finish taps.
   - `STATE.process_split_today[process]` increments via SSE.
   - Derived tiles (avg, eff, abayas, garments) refresh within
     ~100 ms after the SSE post-event poll.
4. Per-tile pills show:
   - Active Workers: `live`
   - Completed Today: `live`
   - Abayas Delivered: `-Xs` (or `-100ms`-style fresh state)
   - Avg Session Time: `-Xs`
   - Efficiency Score: `-Xs`
5. When the SSE lane is busy or events pause, polls sustain tiles at
   `-1s` to `-2s`. When offline for > 5 min, tiles turn `stale`.

## 6. What's still NOT in v1.2.41 (deferred)

- **End-to-end network clock-skew correction** — `state_meta.server_now_ms`
  is the CLOUD's clock, not the factory's. Clock skew between the
  factory's local server and the cloud makes the freshness numbers
  pessimistic by up to the round-trip time. A future v1.2.4x can ship
  a `factory_now_ms` heartbeat from the LAN and report true RTT in
  the pill.
- **Durable-Object-backed SSE** — same rationale as v1.2.40: per-isolate
  fan-out + auto-reconnect covers the use case without paying DO
  minutes. If isolate-eviction frequency ever hurts UX, this is the lever.
- **Auto-update of the bootstrap itself** — the script is in
  `install/REPAIR-UPDATER-BOOTSTRAP.ps1`, but it isn't shipped as
  `extraResources/` to the launcher (only the existing `install/`
  NSIS resources go there). The handler also falls back to
  `process.resourcesPath`. Already wired; tested via the IPC.
