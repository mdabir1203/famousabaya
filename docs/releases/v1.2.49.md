# v1.2.49 — Per-abaya visual distinction ported to the offline dashboard

> **TL;DR:** The factory's offline dashboard (`public/dashboard.html`)
> now carries the same per-abaya visual distinction the cloud day-modal
> has had since v1.2.47: a deterministic left-border tint, an 8px
> swatch dot, a "Custom" pill on `is_custom=1` rows, and audit
> `data-*` attributes for future offline ops scripts. The offline
> `Recent Checker Logs`, `Recent Invoice Logs`, and `Live Active
> Sessions` panels each render the new treatment. Same hash, same
> purple, same audit contract as the cloud — so an operator looking
> at the kiosk's local dashboard sees the same row accent they'd
> see on `dashboard.farewellabaya.com`.

---

## 1. Why

The cloud day-modal shipped the per-abaya accent in v1.2.47 as part
of the visual audit pass. The factory's offline dashboard at
`192.168.0.101:3111/dashboard` (the one the operator looks at most
often — it's the only one open all day on the supervisor's laptop)
was still rendering raw rows with no visual anchor between abayas.
When the same worker does two sessions back-to-back on the same
abaya (CF111 STD-O), the operator's eye couldn't track which row
belongs to which build.

This commit mirrors the v1.2.47 cloud treatment on the three offline
surfaces that render session-style rows:

- **Live Active Sessions** — already had a Custom pill on the "this
  build" cell, now has the full set (border + dot + audit attrs +
  Custom pill on the info row).
- **Recent Checker Logs** — never had any abaya distinction. Now has
  border + dot + audit attrs + Custom pill on the Item column.
- **Recent Invoice Logs** — never had any abaya distinction. Now has
  border + dot + audit attrs (no Custom pill — invoice-maker rows
  don't typically need it; abaya_id is rarely the operator's focus
  on the invoice panel).

## 2. What changed

### 2.1 Three helpers in `public/dashboard.js`

```js
/** Stable HSL accent for an abaya_id. Same multiplicative-hash
 *  formula as ceo-pages.js#edRowAccent so the two dashboards agree
 *  on which abaya gets which border. */
function abayaAccentFor(abayaId) { … }

/** "Custom" pill HTML for an abaya_id when the local catalog has
 *  is_custom=1. */
function abayaCustomPillFor(abayaId) { … }

/** Audit data attributes — stamped on every row that renders a
 *  session-style record. Future offline ops scripts can read the
 *  raw kiosk-tap timestamps without re-querying the LAN server. */
function rowAuditAttrsFor(l) { … }
```

`rowAuditAttrsFor` emits **six** data attributes (matching the
cloud's contract):

| Attribute | Source field | Notes |
|---|---|---|
| `data-session-id` | `<emp_id>-<started_at>` composite | Cloud uses `WL-<emp_id>-<ended_at>` (D1 PK). Offline uses `emp_id + started_at` composite — unique within a boot because `server.js`'s v1.2.43 idempotency guard suppresses dup pushes. |
| `data-emp-id` | `l.emp_id` | `e_bc_<digits>` |
| `data-abaya-id` | `l.abaya_id` | Catalog id |
| `data-abaya-code` | `l.abaya_code` | e.g. `CF111 STD-O` |
| `data-started-at-ms` | `l.started_at` (seconds) | Stamp the raw value; browser multiplies by 1000 only when formatting for display. |
| `data-ended-at-ms` | `l.ended_at` (seconds) | Same — kiosk tap time, never recomputed. |

The last two follow AGENTS.md §2 / §2.2: timestamps are the kiosk's
verbatim `Date.now()` at the moment of Start / Finish tap, preserved
byte-for-byte from the LAN push.

### 2.2 Three rendering surfaces updated

| Surface | Border-tint | Swatch dot | Custom pill | Audit attrs |
|---|---|---|---|---|
| Live Active Sessions | ✅ | ✅ | ✅ (info row) | ✅ |
| Recent Checker Logs | ✅ | ✅ | ✅ (Item col) | ✅ |
| Recent Invoice Logs | ✅ | ✅ | — | ✅ |

The Cloud D1 PK (`WL-<emp_id>-<ended_at>`) doesn't translate cleanly
to offline (no equivalent PK on the LAN side), so offline uses the
composite `emp_id-started_at` for `data-session-id`. The audit
script that consumes these attrs just needs `emp_id` + `started_at`
to look the row up in either system.

### 2.3 Test coverage

`tests/dashboard-per-abaya.test.mjs` — 5 source-grep + 3 behavioral
sandbox tests:

- `abayaAccentFor` is deterministic + same hash formula as cloud
- `abayaAccentFor('')` and `abayaAccentFor(null)` fall back to
  brand purple `#6b5fc1` (so a row with no abaya_id isn't a black
  swatch)
- `abayaCustomPillFor` returns the literal `Custom` HTML only when
  the local catalog's `is_custom` flag is 1, and empty string
  otherwise (empty / null / not-in-catalog all return `''`)
- `rowAuditAttrsFor` preserves `started_at` and `ended_at`
  byte-for-byte (AGENTS.md §2 / §2.2 contract)
- The six audit attrs all appear in `rowAuditAttrsFor`'s body —
  and only from `rowAuditAttrsFor` (no copy-paste duplication)

The sandbox pattern follows `dashboard-live-tick.test.mjs`'s
`computeInShiftSec` / `computeActiveTodaySec` style — extract the
helper as text and execute it with stub globals (`ABAYAS`,
`escapeAttr`) injected via `new Function(...)`.

## 5. Playwright verification — what the factory operator will see

The cloud-side `scripts/verify-deploy.mjs` is the §12 verification
policy wrapper. v1.2.49 doesn't touch cloud surfaces, so the cloud
verification scenarios from v1.2.47 / v1.2.48 continue to pass.

The **offline** dashboard at `192.168.0.101:3111/dashboard` can only
be reached from inside the factory LAN, which the dev machine doesn't
have. The factory operator's first PM2 restart after the auto-update
picks up the new build; a quick visual scan of the three panels
confirms:

- **Live Active Sessions**: each row's left border has the abaya's
  hue, an 8px swatch dot appears in the info row, a "Custom" pill
  appears next to the abaya name when `is_custom=1`.
- **Recent Checker Logs**: each row's left border + swatch dot +
  Custom pill (same convention).
- **Recent Invoice Logs**: each row's left border + swatch dot (no
  Custom pill — invoice-maker panels don't usually need it).

If the operator spots a row without the expected treatment, the
LAN-side `console.log` of the new helpers can be triggered by
running the kiosk in dev mode (`pm2 stop abaya-server && node
server.js`); the helper functions log their arguments to help
debug a missing accent.

## 6. What factory PCs will see

After the next auto-update to `1.2.49`, the offline dashboard
renders the per-abaya accent on every session-style row. No new
buttons, no new panels — just a visual upgrade to the rows the
operator already looks at every day.

The kiosk's Start / Finish flow is unchanged. `req_startWork` and
`req_finishWork` still push the same `session_start / session_finish`
events; the new code in `dashboard.js` is read-only on the pushed
fields.

No factory-side action required. The auto-update flow picks up
`1.2.49` automatically.

## 7. What the operator can verify on their end

Quick checklist after the update:

- [ ] Open `http://localhost:3111/dashboard` (or the LAN IP)
- [ ] Live Active Sessions panel: at least one active session row
      has a colored left border (8px wide) and an 8px swatch dot
      before the abaya name.
- [ ] Recent Checker Logs: same convention. Rows for the same abaya
      have the same color (deterministic hash).
- [ ] Recent Invoice Logs: left border + swatch dot only (no Custom
      pill).
- [ ] DevTools → Elements → click a row → see `data-session-id`,
      `data-emp-id`, `data-abaya-id`, `data-abaya-code`,
      `data-started-at-ms`, `data-ended-at-ms` attributes populated.
- [ ] For an `is_custom=1` abaya (any row with "Custom" pill on the
      cloud), the same row on the offline dashboard also shows the
      pill — same purple, same text.

If any of the above is missing, the auto-update didn't pick up the
new build — check `pm2 list` shows `abaya-server` running, then
restart: `pm2 restart abaya-server`.
