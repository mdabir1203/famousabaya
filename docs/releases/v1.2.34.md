# v1.2.34 — Zombie-filter on the live board

> **TL;DR:** Cloud + offline dashboards now hide forgotten-Finish
> "zombie" sessions from the LIVE ACTIVE SESSIONS list and the Active
> Workers KPI. A zombie = open >8h AND currently outside a shift window.
> The rows stay in D1 / `STATE.active` for data preservation — this is
> UI-only filtering. No factory PC changes needed; the cloud Worker
> updates itself within ~30s of `wrangler versions upload` going 100%.

---

## What was wrong

After v1.2.33 the cloud dashboard could show "Active Workers: 12" with
12 STUCK rows in the LIVE ACTIVE SESSIONS panel — even when no worker
was actually on the floor. The 12 rows were real `active_sessions`
entries in D1 from sessions that started Aug 31 – Sep 10 and never
received a `session_finish` event. The factory's `STATE.active` had the
same 12 rows for the same reason.

The dashboard already labeled them with a red **STUCK** pill — that was
the cue for the operator to investigate. But it still counted them as
"Active Workers" and listed them in the live board, which made the KPI
misleading (the factory could be empty and the cloud still showed N=12).

## What changed

### Cloud Worker (`cloudflare/src/ui/ceo-pages.js`)
- New `isZombieActive(s, nowMs)` helper: returns `true` when
  `(nowMs - started_at) > 8h` AND `outside_shift === true`. For legacy
  rows with no `outside_shift` flag (pre-migration 0016), falls back to
  the local `inWindowClient()` recompute.
- New `liveActiveIds(active, nowMs)` helper: filters zombies out of
  `STATE.active` for the live board and KPI.
- `renderAll()` now sets `kpiActive.textContent = liveActiveIds(active).length`.
- `buildLiveSessionsHtml()` now iterates `liveActiveIds(active, nowMs)` instead
  of raw `Object.keys(active)`.

### Offline dashboard (`public/dashboard.js`)
- Same `isZombieActive` + `liveActiveIds` helpers (mirror).
- `renderKPIs()` Active Workers count now uses `liveActiveIds`.
- `renderLiveSessions()` now skips zombies from the live board.

### Tests (`tests/dashboard-live-tick.test.mjs`)
- New test #13: cloud-side behavioral + source-level audit. Covers all
  five edge cases (fresh / zombie / long-shift / lunch break / legacy
  flag) plus the real Sep 14 factory snapshot (5 of the 12 zombies,
  asserts all are hidden).
- New test #14: offline-side mirror. Pins the same rule in
  `public/dashboard.js`.

Total: 14 dashboard-live-tick tests, all passing. (`admin-close-stale-cloud-push.test.mjs`
test #1 is a pre-existing flake about a specific employee — unrelated
to this fix, fails the same way on unmodified main.)

## Why 8 hours

The cloud's `is_stale` flag (which drives the existing **STUCK** pill)
uses a 2-hour threshold. That's correct for "is this session likely a
forgotten-Finish" — a worker who taps Start and walks away for 2h during
a shift gap is suspicious.

But the **Active Workers KPI** needs a longer threshold. A worker can
legitimately step away for a 1-hour lunch break, an afternoon meeting,
or a slow period between orders. The 2h threshold would falsely hide
people who are still on shift. 8 hours matches the cloud's
`MAX_OUT_OF_SHIFT_BEFORE_DEAD` heuristic and the local
`shared/live-row-state.cjs` definition of "definitely gone home".

If you want a different threshold, change the `ZOMBIE_MAX_AGE_SEC`
constant in **both** `ceo-pages.js` and `dashboard.js`. The same value
on both sides keeps the two dashboards in lock-step.

## What factory PCs will see

Nothing. The local dashboard update ships inside this same release and
gets picked up by the auto-updater. No new env vars, no new CLI flags,
no PM2 restart needed.

## What the operator will see

- **Today (empty factory):** "Active Workers: 0" + "No active sessions
  right now" panel. The 12 zombie rows are invisible — but still
  recoverable from D1 if you ever want them.
- **Today (active shift):** identical to before — workers show up
  normally. As soon as a session crosses the 8h mark AND the shift
  window closes, it disappears from the live board.
- **Historical reports (Daily / Weekly / Monthly):** unchanged. The
  historical `sessions` table is not affected by this filter.
