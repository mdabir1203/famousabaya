# v1.2.25 — D1 free-tier mitigation: cache hot-path config reads

> **Released:** 2026-09-05
> **Severity:** HOTFIX (factory ingest was silently broken)
> **Scope:** Cloudflare Worker only — no install/launcher change required
> **Tag:** `v1.2.25`

## TL;DR

The factory's `/api/event` ingest was returning `500 Worker threw
exception` for the past several hours because the Cloudflare D1
**free-tier daily row-read limit** (5M rows/day) was exhausted. Every
ingest call did a fresh D1 row-read for the working-hours config, and at
~1 ingest every few seconds × ~21 hours of factory uptime, that read
count crossed the free-tier threshold.

**Fix:** in-memory caches with TTL + synchronous save-side invalidation
on the two hot-path config reads:

| Function | Caller frequency | TTL | Effect |
|---|---|---|---|
| `getWorkingHoursConfig` | every `/api/event` (1/ingest) | 60s | 1 read/min/isolate instead of 1/event |
| `getOfficeNumbers` (tickets) | every `POST /api/tickets` | 5 min | 1 read/5min/isolate instead of 1/ticket |

Caches are **per-Worker-isolate** (Cloudflare's natural memory model),
with an in-flight-promise pattern so a burst of N concurrent ingests
during a cold cache collapses to **one** D1 read, not N.

After deploying, the factory's `POST /api/event` returns 200 again and
the CEO dashboard resumes real-time updates.

## Why this happened

The factory server pushes events to the cloud continuously. The
`handleIngest` path in `cloudflare/src/handlers/ingest.js` calls
`getWorkingHoursConfig(env)` to determine whether a session_start is
within the configured working windows. That function did a D1 read on
every call:

```js
// before (v1.2.20 → v1.2.24)
export async function getWorkingHoursConfig(env) {
  const row = await env.DB.prepare('SELECT v FROM worker_settings WHERE k = ?')
    .bind(WORKING_HOURS_KEY).first();
  return workingHoursConfigFromRow(row);
}
```

At 1 ingest every 3-5 seconds (each active session pushes on
session_start + session_finish, and the factory usually has 6-15 active
sessions), that's ~6,000-15,000 reads/day just for working-hours. Add
the same pattern in `tickets.js` for office numbers, the read count
climbed into the millions.

D1 free tier = **5M row reads/day**. We crossed it sometime in the
morning of 2026-09-05. Every subsequent ingest hit the
`D1_ERROR: Your account has exceeded D1's free tier daily row read
limit` error and the Worker returned 500.

The factory server's retry logic would re-send, but those also got 500,
so the queue built up. The CEO dashboard showed no new data.

## What changed

### Worker source

**`cloudflare/src/working-hours.js`** — cache the working-hours read:

```js
const WORKING_HOURS_CACHE_TTL_MS = 60_000;
let _whCache = null;        // { cfg, fetchedAt }
let _whInflight = null;     // Promise<cfg> | null

export async function getWorkingHoursConfig(env) {
  const now = Date.now();
  if (_whCache && (now - _whCache.fetchedAt) < WORKING_HOURS_CACHE_TTL_MS) {
    return _whCache.cfg;
  }
  if (_whInflight) return _whInflight;   // collapse concurrent bursts
  _whInflight = (async () => {
    try {
      const row = await env.DB.prepare('SELECT v FROM worker_settings WHERE k = ?')
        .bind(WORKING_HOURS_KEY).first();
      const cfg = workingHoursConfigFromRow(row);
      _whCache = { cfg, fetchedAt: Date.now() };
      return cfg;
    } finally { _whInflight = null; }
  })();
  return _whInflight;
}

export async function saveWorkingHoursConfig(env, cfg) {
  // ... unchanged D1 write ...
  _whCache = null;            // synchronous invalidation
  return normalized;
}
```

**`cloudflare/src/handlers/tickets.js`** — same pattern for office
numbers, with a 5-minute TTL (this config changes rarely):

```js
const OFFICE_NUMBERS_CACHE_TTL_MS = 5 * 60_000;
let _officeCache = null;
// ... in getOfficeNumbers() ...
// ... _officeCache = null in setOfficeNumbers() ...
```

## Why TTL = 60s (not longer)

Working hours DO change (CEO adjusts the shift schedule occasionally),
and the CEO's save goes through the same isolate that cached the value,
so the synchronous invalidation covers the common case. The 60s TTL is
the backstop for cross-isolate staleness — if a CEO saves from a
different isolate, the old isolate will pick up the new value within
60s.

A longer TTL would compound the staleness risk for marginal gain
(60s already collapses ~99% of reads under steady state).

## Why not just upgrade to D1 paid?

We considered it. The Workers paid plan is $5/month for 25B reads/month
(~$0.4B/day). But the cache is **defense in depth** — even on a paid
plan, the per-event D1 read was a 5-10ms latency hit on the hot path.
The cache cuts that to ~0ms for the cached read.

So the cache is shipped regardless of the plan tier. The paid-plan
upgrade is a follow-up question, not a blocker.
