AbaYa-Track · a factory in three dimensions

Three boxes. One source of truth. And a CEO who never sees a gap.

A factory laptop in Dubai writes Start/Finish events to memory, durably saves them to disk, retries pushing them to a Cloudflare Worker, and reconciles any lost ones. The result is a live line you can read from any browser in the world, even if the WAN died.

01 · physical

Three boxes. One source of truth.

The factory laptop holds everything. The cloud holds a copy. The CEO is a window.

Think of it like a kitchen. The factory is the kitchen where the food is actually cooked. The cloud is the recipe notebook that lives somewhere else, in case the kitchen burns down. The CEO is the person who walks up to the window and asks what's cooking. The kitchen doesn't trust the notebook. The notebook just tries to keep up.

Read this as
  • Purple arrows are the realtime socket path (kiosk to server.js).
  • Cyan arrows are HTTPS to the Cloudflare Worker (factory to cloud, tablet to cloud).
  • Red dashed is the durable retry path through the NDJSON queue. It lives on disk, never in the runtime.
  • Green arrows are authenticated or TLS-secured channels (CEO cookies, HMAC, bridge secret).
  • Blue is the dispatch service bridge, which is independent of the factory push path.
  • The factory talks to the cloud over two separate bridges: its own client and the dispatch service's bridge. A WhatsApp outage does not stall the line.

02 · boot

Eighteen loops. None of them kill the others.

When the laptop starts, it sets up eighteen timers. Every one of them is wrapped in a safety net so a network failure cannot crash the system.

Imagine a restaurant opening at 7am. The head chef turns on the stove, the dishwasher starts, the cashier boots the register, the delivery driver checks the schedule. Each of those is a separate loop. If the internet is down, the cashier still opens the till with yesterday's numbers. The head chef doesn't wait for the delivery driver to come online. That's this server. The factory can boot with no WAN, no D1, no LAN share. The kiosk still works.

Read this as
  • Steps 1 to 4 happen before listen, in module top-level: middleware, push layer, asset sync. They never block boot.
  • Steps 5 to 18 happen inside the listen callback, in the order shown. Each is a one-liner that schedules a setInterval.
  • The four fire-and-forget chains (3, 4, 6, 7) run concurrently; the rest are synchronous schedule calls.
  • Every interval is a defensive default. OFFLINE_REPORT_DIR, SQLITE_SNAPSHOT_INTERVAL_MS, ROSTER_PULL_INTERVAL_MS can all be overridden via env.

03 · runtime

Tap Start. One row. The dashboard blinks.

A worker scans a barcode. The system writes one row to memory, durably saves it to disk, and tries to push it to the cloud. The dashboard updates in milliseconds.

When a tailor sits down at a sewing machine, they scan a card. That single tap kicks off maybe thirty things, but only one of them has to finish before the tailor can start sewing. The rest happen after, in the background, and if any of them fail, the system quietly retries. The tailor never waits. The CEO never sees a gap.

Read this as
  • The callback path (the solid horizontal arrows) is what the kiosk sees. Synchronous in-memory work plus the response.
  • The shadow paths (dashed) are setImmediate. Durable writes that do not block the user.
  • The cloud push is the only outbound call that can return 4xx/5xx, and when it does, the row is queued, not lost.
  • The rejected queue exists for client errors that will not recover (bad shape, schema mismatch). It is a forensic record, not a retry buffer.
  • The drain path runs independently every 30 s. It picks up queued rows and replays them oldest-first.

04 · cloud write

One network call. Four rows. Atomic.

When the cloud receives an event, it does one round trip to the database. Four rows get written. Either all four land or none of them do. There is no in-between.

Picture a bank transfer. You don't want to subtract from one account and then fail to add to the other. Either the money moved or it didn't. The cloud here does the same trick, four times over, every time. The four writes, log the session, clear the active row, bump the daily counter, update the abaya timeline, all commit together. If any one of them fails, the whole batch rolls back. The factory pushes the same event again, the database ignores the duplicate, and the system stays consistent.

Read this as
  • The batch is atomic. D1 either commits all four statements or rolls them all back. There is no partial state.
  • sessions.id is deterministic: WL-{emp_id}-{ended_at}. INSERT OR IGNORE makes every replay safe.
  • daily_stats is the only non-idempotent table by design. It is the per-day cumulative counter, not a row log. UPSERT on stat_date means the same Finish can be replayed forever and the count only ticks once per real session.
  • abaya_time_map is conditional. It only writes if the Finish carried an abaya_id.

05 · resilience

Three independent timers. None of them trust the others.

If the cloud missed something, three other timers will eventually catch it. They run on different schedules, write to different files, and never coordinate.

A 5G tower in Dubai can drop for a second and the line doesn't stop. The factory laptop doesn't trust the cloud. The cloud doesn't trust the factory laptop. Each one has its own notion of what happened, and they meet up on a schedule. If the line keeps moving for six hours with no internet, the laptop is still fine. When the WAN comes back, the cloud catches up within five minutes. If a row was lost in the queue, the periodic reconcile will find it by diffing the local state against the cloud.

Read this as
  • The three tiers are independent. They run on different timers, write to different files, and never coordinate.
  • If a row is lost on the push path, the reconcile tier will eventually find it on the diff path.
  • If the factory goes offline, the cloud-today mirror still serves the CEO dashboard from whatever rows made it through.
  • The auth-error exception is the only case where the queue is preserved on disk rather than retried. The secret has to be fixed first.

06 · ceo

A password becomes two cookies. The page checks them every time.

Login → JWT pair → HttpOnly cookies. The dashboard is server-rendered HTML+JS, inlined, 221 KB. No CDN. No external scripts.

When the CEO opens the URL, the Worker checks two cookies. If they're good, the Worker builds the entire HTML page on the server and ships it down. The page then polls every 3 seconds for a fresh batch of KPIs. The cookies have a 30-minute life and a 7-day refresh token. The CEO doesn't think about this. They just see the dashboard.

Read this as
  • There are three independent secrets on this Worker: INGEST_SECRET, CEO_JWT_SECRET, and X-Bridge-Secret. Compromise of one does not affect the others.
  • The CEO dashboard is server-rendered (221 KB inlined HTML/JS). It does not depend on any external CDN, so it renders even when third-party trackers are down.
  • The browser's long-poll (3 s) + 10-stmt batch means the CEO sees a consistent snapshot every 3 seconds, not a stream of partial updates.
  • Cookies are HttpOnly · SameSite=Lax. The JWT never reaches JavaScript, so an XSS in a future dashboard widget cannot exfiltrate the token.

07 · catalog

Edit on one laptop. Every other laptop sees it within a minute.

The factory is canonical. The cloud is downstream. A new laptop with no local data seeds itself from the cloud instead of falling back to demo data.

If the operator renames a process or adds a new abaya on laptop A, the change goes to the cloud in one PUT. Laptop B, C, and D poll the cloud every 60 seconds. The first one to notice the version bump pulls the new list and applies it. A new laptop — one that has never seen the catalog — boots up empty and asks the cloud for the full thing. The bundled demo data is the fallback, not the source.

Read this as
  • The catalog PUT is all-or-nothing. The Worker runs DELETE + INSERTs in a single D1.batch, so a partial write can never leave a laptop with a half-edited catalog.
  • The version counter (catalog_meta.v) is the cache buster. Peers only re-apply if the version they see is newer than the version they have.
  • The fresh-install seed path is what lets a new factory laptop boot from cloud data instead of the bundled demo catalog. The same path also pulls the employee roster.
