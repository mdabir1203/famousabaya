01
physical

Where the bytes live

Three tiers. Six protocol boundaries. One identity — FACTORY_TZ=Asia/Dubai. The top row is the operational flow; the bottom row is everything else that quietly keeps it honest.

client factory tier cloud tier (Worker · D1 · R2) durable local store offline-retry queue authenticated / TLS dispatch service
Read this as
  • Purple arrows — realtime socket path (kiosk to server.js)
  • Cyan arrows — HTTPS to the Cloudflare Worker (factory to cloud, tablet to cloud)
  • Red dashed — durable retry path through the NDJSON queue (lives on disk, never in the runtime)
  • Green arrows — authenticated or TLS-secured channels (CEO cookies, HMAC, bridge secret)
  • Blue — the dispatch service bridge, which is independent of the factory push path
  • The factory talks to the cloud over two separate bridges: its own client (push queue + state pull) and the dispatch service's bridge. A WhatsApp outage does not stall the line.
02
boot

server.js — the boot cascade

The server.listen callback is the real orchestrator. Eighteen steps, two columns, zero fatal failure paths — every fire-and-forget chain is wrapped in .catch(_=>{}).

Read this as
  • Steps 1–4 happen before listen (in module top-level) — middleware, push layer, asset sync. They never block boot.
  • Steps 5–18 happen inside the listen callback, in the order shown. Each is a one-liner that schedules a setInterval and optionally a setTimeout or setImmediate.
  • The four fire-and-forget chains (3, 4, 6, 7) run concurrently; the rest are synchronous schedule calls.
  • Every interval is a defensive default — OFFLINE_REPORT_DIR, SQLITE_SNAPSHOT_INTERVAL_MS, ROSTER_PULL_INTERVAL_MS can all be overridden via env.
03
runtime

Start / Finish — every byte, every function

The most-traveled path in the system. Trace this once and you understand the rest. Solid arrows are the user-visible callback; dashed arrows are setImmediate durability.

Read this as
  • The callback path (the solid horizontal arrows) is what the kiosk sees — synchronous in-memory work plus the response.
  • The shadow paths (dashed) are setImmediate — durable writes that do not block the user.
  • The cloud push is the only outbound call that can return 4xx/5xx, and when it does, the row is queued, not lost.
  • The rejected queue exists for client errors that will not recover (bad shape, schema mismatch). It is a forensic record, not a retry buffer.
  • The drain path runs independently every 30 s; it picks up queued rows and replays them oldest-first.
04
cloud write

handleIngest — the D1 batch

One HTTP call. Four tables touched in one atomic round trip. Idempotent on the row, atomic on the batch. The reconcile loop depends on this — it can re-push the same row 100 times and D1 will hold exactly one.

Read this as
  • The batch is atomic. D1 either commits all four statements or rolls them all back. There is no partial state.
  • sessions.id is deterministic — WL-{emp_id}-{ended_at} — so INSERT OR IGNORE makes every replay safe.
  • daily_stats is the only non-idempotent table by design. It is the per-day cumulative counter, not a row log. UPSERT on stat_date means the same Finish can be replayed forever and the count only ticks once per real session.
  • abaya_time_map is conditional — it only writes if the Finish carried an abaya_id.
05
resilience

Three independent safety nets

A factory can lose its WAN mid-shift. None of these three mechanisms know or care about the others. They sit on a single time axis — sub-second, thirty seconds, five minutes.

Read this as
  • The three tiers are independent. They run on different timers, write to different files, and never coordinate.
  • If a row is lost on the push path, the reconcile tier will eventually find it on the diff path.
  • If the factory goes offline, the cloud-today mirror still serves the CEO dashboard from whatever rows made it through.
  • The auth-error exception is the only case where the queue is preserved on disk rather than retried — the secret has to be fixed first.
06
ceo

CEO auth & dashboard render

Cookie-based JWT pair. Login → dashboard server-rendered → KPI batches in one round trip. A leaked ingest secret only enables a narrow GET; CEO and dispatch use independent secrets.

Read this as
  • There are three independent secrets on this Worker: INGEST_SECRET, CEO_JWT_SECRET, and X-Bridge-Secret. Compromise of one does not affect the others.
  • The CEO dashboard is server-rendered (221 KB inlined HTML/JS). It does not depend on any external CDN, so it renders even when third-party trackers are down.
  • The browser's long-poll (3 s) + 10-stmt batch means the CEO sees a consistent snapshot every 3 seconds, not a stream of partial updates.
  • Cookies are HttpOnly · SameSite=Lax — the JWT never reaches JavaScript, so an XSS in a future dashboard widget cannot exfiltrate the token.
07
catalog

Catalog write & propagation

Factory is canonical. Cloud is downstream. Every other factory laptop sees the new version within 60 s. A new laptop with no xlsx seeds itself from the cloud instead of falling back to demo data.

Read this as
  • The catalog PUT is all-or-nothing — the Worker runs DELETE + INSERTs in a single D1.batch, so a partial write can never leave a laptop with a half-edited catalog.
  • The version counter (catalog_meta.v) is the cache buster — peers only re-apply if the version they see is newer than the version they have.
  • The fresh-install seed path is what lets a new factory laptop boot from cloud data instead of the bundled demo catalog. The same path also pulls the employee roster.
