1 What is this app?

AbaYa Track is a hybrid factory-floor productivity system for an abaya (Islamic garment) factory. Workers tap their employee code on a tablet, scan an abaya barcode, do their station's work (cutting, stitching, embroidery, buttons, stone work, invoice, packaging, QC), then tap Finish. The factory server times them inside configured shift windows and pushes events to a Cloudflare Worker so the owner (CEO) can read live dashboards and daily/weekly/monthly reports from any browser, anywhere.

Local-first. The factory never blocks on the cloud. If the internet drops, all floor operations keep working and event payloads are queued to a JSONL file that auto-replays when the link is back.
Three user groups. Factory operators (kiosk tablets), supervisors (LAN dashboard), executives (CEO cloud dashboard), plus IT/admin for installs and updates.

9 Persistence & offline story

Three independent local stores back up the in-memory state, plus a fourth offline-resilient queue for cloud writes.

flowchart TB subgraph IM["In-memory (server.js)"] direction LR A1["ACTIVE_SESSIONS{}"] A2["COMPLETED_LOGS[]"] A3["EMP_PERF[]"] A4["abayaCatalog[]"] A5["EMPLOYEES[]"] end IM -->|"setImmediate after every mutation\n+ setInterval 60s"| OR["offline-report-store.cjs\n→ data/offline-dashboard-reports/dashboard-offline-latest.json\natomic .tmp + rename\nretention: OFFLINE_SNAPSHOT_RETENTION_DAYS"] IM -->|"setInterval SQLITE_SNAPSHOT_INTERVAL_MS (default 5m)\n+ setTimeout(5s) on boot\n+ after every finish"| SQ["sqlite-snapshot.cjs\n→ data/sqlite-snapshots/abaya-snapshot-YYYYMMDD-HHMMSS.db\nreal SQLite via sql.js\nmatches cloudflare/schema.sql\n+ signed manifest (SNAPSHOT_SIGNING_SECRET)\nNTFS ACL hardening via snapshot:harden"] IM -->|"On cloud failure (timeout, 5xx)"| NDJ["ceo-ingest-queue.jsonl\nappend-only NDJSON\n.ceo-ingest-rejected.jsonl for permanent 4xx\ndrainCeoIngestQueue() on\nCEO_INGEST_RETRY_MS (default 30s)"] SQ -->|"yarn snapshot:import --to-d1 [--remote]"| D1[("D1 abaya-db")] NDJ -->|"Retry until 2xx\nor move to rejected"| CW["Cloudflare Worker\nPOST /api/event"] Boot["On server start"] --> OR2["load latest offline snapshot\nreviveActiveSessionsFromSnapshot()\nfilter by RESTORE_ACTIVE_SESSION_MAX_AGE_MS (default 48h)"] OR2 --> IM
Layered durability. In-memory is fast but volatile; offline JSON is human-readable; SQLite is the canonical local copy; the NDJSON queue survives full power loss and reorders gracefully.

Restore rules on startup

  • In-progress sessions (kiosk) are revived from the latest snapshot if started_at is within RESTORE_ACTIVE_SESSION_MAX_AGE_MS (default 48h) and the employee still exists in the current roster.
  • Completed logs are restored subject to OFFLINE_LOG_WINDOW_MS (default = entire history, still capped by STATE_LOG_MAX_ROWS).
  • Catalog & roster are always re-fetched from the cloud (60s) and reloaded from the local xlsx (1h) on every boot — never trusted from the offline snapshot.
  • Graceful shutdown (SIGINT/SIGTERM) flushes both persistOfflineDashboardReport() and persistSqliteSnapshot() before process.exit(0). An OS power-cut may still lose the last in-progress session.

12 Ops & maintenance

Day-to-day operating commands. The repo's START HERE.txt and START-HERE-BUILD-INSTRUCTIONS.txt walk through these.

Install / launch

  • First install: install\INSTALL.bat (or yarn setup) — Corepack, Yarn 4 PnP deps, .env bootstrap, Desktop shortcut. No PowerShell required for the install itself.
  • Daily start (classic): install\LAUNCH-ALL.bat — optional Cloudflare tunnel, runtime picker (Node or Bun), server + watcher in separate consoles, auto-start at Windows logon.
  • Always-on (PM2): powershell -NoProfile -ExecutionPolicy Bypass -File install\SETUP-PM2-BOOT.ps1 once; then pm2 status, pm2 logs abaya-server, pm2 reload all.
  • Electron GUI (optional): tools/desktop-launcher with electron-updater OTA from R2. Same processes, one window.
  • Cloud deploy: yarn deploy:all or install\DEPLOY-ALL.ps1 (Worker + Pages + tunnel).
  • Single-EXE installer: yarn package:installer:win produces an NSIS installer under dist/desktop-launcher/.

Snapshots & integrity

  • Manual snapshot: yarn snapshot:db writes a fresh abaya-snapshot-*.db.
  • Info: yarn snapshot:info shows metadata.
  • Import to D1: yarn snapshot:import --to-d1 [--remote].
  • Tamper protection: set SNAPSHOT_SIGNING_SECRET, then yarn snapshot:harden (NTFS ACLs) and yarn snapshot:verify in a scheduled task.
  • Tests: yarn test (unit), yarn test:system (smoke), yarn test:offline-store, yarn qa:qc, yarn verify:employee-xlsx.
  • Live eval: yarn evaluate:rollout / yarn evaluate:live.
  • CEO state check: yarn verify:ceo.

13 Risks & technical debt (worth knowing)

From docs/SYSTEM_DESIGN.md §12 and a fresh scan of the source.

  • Monolith server.js (3,712 lines). Easy to read, hard to unit-test. Routes, persistence, push, watchers, alerts all share one closure.
  • No horizontal scale — single Node process, in-memory state. Adding a second node would require moving state out (Redis or always-on DB).
  • OS power-cut window. The default 60s persistOfflineDashboardReport cadence can lose the last minute of work. The 48h restore window is generous but not infinite.
  • No build pipeline for the client. public/kiosk.js and public/dashboard.js are loaded directly. No minification, no module bundling, no source maps.
  • Factory socket/read APIs are unauthenticated by default. Security relies on the LAN boundary (or Tailscale). CORS: * is enabled.
  • CEO token can land in query string (bootstrap via ?token=). Reduces to cookie after the first 302, but the URL ends up in browser history and referer logs.
  • No secret rotation or audit trail. Static CF_INGEST_SECRET, CEO_JWT_SECRET, ASSET_UPLOAD_SECRET.
  • Multi-writer catalog (Watcher vs Excel vs Admin PUT) can race. Last-writer-wins by version timestamp; no CRDT.
  • Domain constants duplicated across public/data.js, cloudflare/src/domain/process.js, server.js's DEFAULT_FACTORY_WORK_TYPES, and tools/catalog-watcher/config.json. Drift risk.
  • .env.example has unresolved git merge markers at lines 123–139 (<<<<<<< HEAD / ======= / >>>>>>> 10247c8...) around the ABAYA_UPDATE_MIRROR_BASE_URL docs. Cosmetic but worth a clean resolve next time you touch that file.
  • Stale 1 and rows files at the repo root (both 0 bytes) — leftover from a paste / Excel export. Not a bug, but they will show up in git status.
  • items_export.xlsx and other samples sit in the repo root; they're convenient for manual testing but probably shouldn't be tracked long-term.

Where the system shines

  • Offline resilience. NDJSON queue + json snapshot + sqlite snapshot = three independent durability layers, plus a reconcile loop that pulls cloud truth into the factory.
  • Local-first by design. Cloud outage never affects floor operations.
  • Portable single-folder install. install\LAUNCH-ALL.bat downloads a portable Node 20, sets up deps, creates a Windows Startup shortcut — runs from a USB stick if you need it to.
  • Defense in depth on persistence. Tamper-protected SQLite snapshots, NTFS ACL hardening, signed manifest, scheduled verification.
  • Three independent deployment shapes: batch launcher (classic), PM2 (always-on), Electron (GUI with OTA updates).
